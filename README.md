# 梯户模拟器

`tihu`

销售告诉你的是「两梯四户」。他不会告诉你，一栋三十三层的楼在早上七点五十到
八点二十之间，有多少人同时在按同一个下行键。他也不会告诉你，第九层的人平均
要被跳过两趟才挤得进去。

梯户模拟器把三件事算清楚：

- 等多久来
- 来了挤不挤得上
- 进去之后还要晃多久到

它是一个不需要服务器的静态网页，也是一个能吃满 CPU 的命令行扫描器。两种形态
共用同一套 Rust 仿真内核，所以结果不会打架。

---

## 现在的进度

**内核已经能用，外壳还没写。** 这句话必须写在最前面，免得你照着下面的命令敲了
半天发现没有那条命令。

| 部分 | 状态 |
| --- | --- |
| 仿真内核 `tihu-core` | 能跑。运动学、客流、停靠、挤梯、走楼梯、超载死锁、分区停靠都在 |
| 命令行 `tihu-cli` | 空壳。`run`、`sweep`、`bench`、`evolve` 都还没写 |
| 网页绑定 `tihu-wasm` | 空壳 |
| 网页 `web/` | 空目录 |
| 基准 `benches/` | 空 |
| 验收脚本 `harness/` | 空 |

想现在就看数字，只能跑内核自带的例子：

```bash
cargo run --release --example repro -p tihu-core
```

它会跑四栋楼各一次早高峰，把耗时、上梯人数、平均等待、P90 等待、往返时间打印
出来。这是目前唯一能跑的东西。

## 楼层是怎么编号的

**层号 1 是主入口层**，就是住户进出大楼的那一层。住宅层从 2 往上排，地下层用
负数，B1 是 -1，B2 是 -2。层号 0 不存在。

所以一栋「十八层住宅」的顶层号是 19。你说层数时说的是住宅层数，工具里存的是
最高层号，差一个主入口层。

主入口层默认不住人。它可以是架空层，也可以是商铺，也可以住人，看
`ground_floor_residential` 这个开关。

## 电梯分高低区、单双层停靠

这是真实楼盘里最常见的一类设计，所以工具必须支持。写法很简单：

```rust
// 一部只停单层，一部只停双层
cars[0].stops = StopSpec::parity(true);
cars[1].stops = StopSpec::parity(false);

// 高低区分开，低区管 1 到 15 层，高区管 16 到 33 层
cars[0].stops = StopSpec::zone(1, 15);
cars[1].stops = StopSpec::zone(16, 33);

// 直接枚举要停的楼层
cars[0].stops = StopSpec::list([1, 5, 9, 13]);
```

几种写法可以叠加，用 `StopSpec::union` 取并集。单双层那两种写法会自动把主入口层
与所有地下层包含进来，否则地下车库会没有一台车愿意去。

**没照做会被拦下来。** 如果某一层没有任何一台轿厢停靠，运行前就会报错。如果
某一层住了人，却没有一台轿厢同时停靠这一层与主入口层，也报错。后一条是分区梯
最容易踩的坑：低区梯只停 1 到 15 层，高区梯只停 16 到 33 层，两边都不去主入口，
那所有人出门之后都回不了家。

每台轿厢还可以指定初始停在哪一层，`cars[i].initial_level`。

### 为什么大多数时候不需要这个开关

如果你只是想让某台梯慢一点，把耗时加一个常数或者乘一个常数就够了。分区停靠
不一样。**一台只停单层的梯，它的服务楼层集合是离散的，这会影响它怎么扫楼，也
会影响哪些乘客根本挤不上它。** 这类差别乘一个常数是模拟不出来的，所以工具里
单独建了停靠楼层这个维度。

## 客流是怎么生成的

所有乘客在仿真开始之前一次性生成完。这样换一个调度算法，楼里还是同一批人。
这是公平比较两个算法的前提。

### 一次出门，或者出门加回家

每位乘客带一到两条行程腿。只带一条的人出门就到目的地。带两条的人先到某一层，
在那一层停一段时间，再从那里回来。

后一种是条件性需求。真实场景里对应的是：下到车库拿个东西再上楼，送孩子到楼下
再回家，等等。停留时间在生成乘客时抽定，所以同一份种子跑两次，这些人的行为
完全一致。

```rust
// 五分之一的出门人会折返，返程前平均停留十五分钟
traffic.return_ratio = 0.2;
traffic.return_dwell_s = 900.0;
```

### 早晚高峰与地下车库

早高峰的主流是从住宅层往下走，晚高峰反过来，从主入口层往上走。两个方向都有
一小撮人走反向。有地下车库时，一部分人直接下到车库，也有一部分人从车库上楼。

### 有人会走楼梯

两种。一种是出门前就决定不坐电梯的，集中在低楼层，全楼比例落在百分之二到
百分之五。另一种是等得不耐烦、半路改走楼梯的，单独统计。第二种可以关掉：

```rust
stairs.abandon_after_s = 0.0;   // 谁也不中途弃梯
```

### 有人会多按

低楼层的人等下行等不来，把上行也按下，上了车跟到顶层再折返下来。对个人这笔账
常常划算，对全楼每台被占去做无用功的轿厢都在挤压别人。工具支持这个行为的比例
扫描，也支持同时呼叫多台（需要独立按钮面板）。

## 高速梯刹不住的那一层

电梯以额定速度跑着的时候，有人按下它正前方的那一层，它不一定停得住。刹停需要
一段距离，速度越高这段越短不了。工具里按运动曲线算这段距离，来不及停就照直
开过去，那一次的越站单独计数。

换来的是两个真实效应。高速梯在接下来连续的几层都停不了。低速梯几乎不会漏掉
任何一层。哪一层住户的体验更好，这里能算出来。

## 写一个新的调度算法

这个仓库同时是电梯调度算法的试金石。写一个新算法通常是一百行以内的事，不需要
改动内核的任何一行。完整说明在 [`docs/DISPATCH_API.md`](docs/DISPATCH_API.md)。

最关键的一条：**算法只回答「下一程去哪」，停不停由内核定。**

```rust
impl Router for MyRouter {
    fn next_leg(&self, v: &RunView<'_>) -> Leg {
        match v.extreme(Dir::Down) {
            Some(f) if f < v.level() => Leg::Down(f),
            _ => Leg::Park,
        }
    }
}
```

内核接管停靠之后，算法无论怎么写都不会路过该停的楼层，也不会停在没活可干的
楼层。你只需要把路选好。

## 关于准确度

这是一个量级工具，不是电梯招投标依据。

真实性能受厂家群控算法、开关门延迟、有没有并联、有没有地下层、住户错峰习惯的
影响。模型里每个默认值都标了出处，查不到出处的都写了「待标定」，详见
[`docs/MODEL.md`](docs/MODEL.md)。

想让它贴近某一栋具体的楼，需要在现场掐表反推参数。这个功能还没有写。

---

## 能不能上 GPU

不能，至少现在不能。理由与可选方案写在 [`docs/GPU.md`](docs/GPU.md)。一句话版本
是：真正的重活是「几百万次互不依赖的小仿真」，多核 CPU 就是这种负载的最优解，
上 GPU 只会把逐位可复现丢掉。
