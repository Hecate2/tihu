## 3. 基准怎么跑

```
cargo bench                              全部
cargo bench --bench single_run           单次仿真
cargo bench --bench sweep                批量扫描吞吐
cargo bench --bench kinematics           运动学公式
cargo bench --bench dispatch             各替换点的决策开销
make bench-table                         重新生成 DISPATCH_API 里的对比表
```

基准用 criterion，结果落在 `target/criterion`。CI 里存历史曲线，性能倒退会报警。

### 3.1 记录在案的信息

每次发布性能数字，必须同时记录：

```
commit 号
CPU 型号与核数
操作系统与 Rust 版本
构建的 profile，以及目标平台的特性开关
是否开启了超载死锁等可选行为
```

少了任何一项，那个数字都不可比。

## 4. 已知瓶颈在哪里

按预期的影响排序。**这是预测，落地之后要用火焰图验证，不成立就删掉这段。**

1. **随机数**。每秒要抽几百万次。手写 PCG32 纯整数实现，保持在个位数纳秒。循环里不许出现 trait 对象调用和外部库的函数链。
2. **Boarding 循环**。每次停靠对每个等待团掷一次骰子，是热点。小规模热点可以考虑用定点整数代替浮点做概率比较，是否更快待验证。
3. **派梯估算**。`load_aware_eta` 这类算法要做前向推算，是二次热点。把每个场景中不变的部分缓存起来。
4. **事件堆**。元素数量只有几十，`log` 项几乎免费，但 `BinaryHeap` 的常数和可预测性需要实测。
5. **内存的局部性**。每层一个等待队列。单队列元素通常只有几十个，用固定容量的内联数组比堆容器更省。

## 5. 打算怎么加速

| 手段 | 适用层面 | 风险 |
| --- | --- | --- |
| 零空间 allocating 与预分配 | 全局 | 无 |
| 并行数组 layout 取代结构数组 | 热字段 | 代码变难读 |
| 泛型单体化取代动态派发 | 替换点 | 编译时间变长 |
| rayon 多线程 | 批量扫描 | WASM 环境不可用 |
| analytics 预筛 | 超大网格 | 多一套实现要维护 |

**analytics 预筛要谨慎加。** 用解析公式把明显没希望的组合先筛掉，听起来很美，但它引入了第二套逻辑。两套一旦不一致，给出的是错答案。至少要先有办法验证两者一致。至少要先有办法验证两者一致。也有可能不必加，先把原生速度做出来再说。

## 6. WASM 特别要量什么

- **启动开销**。`instantiateStreaming` 的耗时和 base64 版本的差异
- **首屏体积**。它决定了用户要等多久才能看到第一张图
- **单次调用的边界开销**。批量接口相对单条调用省了多少
- **和原生逐位一致**。这一条是正确性要求，不只是性能问题
