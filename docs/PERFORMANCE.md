## 2. 单次仿真耗时

### 2.1 实测：repro 四栋楼

由 `cargo run --release --example repro -p tihu-core` 产出。机器是 Apple M4 Pro，14 核，macOS 15.7.5，release profile 开了 LTO 与 opt-level 3。

| 配置 | 乘客 | 上梯 | 单跑耗时 |
| --- | --- | --- | --- |
| 5 层住宅，一梯四户 | 20 | 20 | 0.14 到 0.24 ms |
| 18 层住宅，二梯四户 | 156 | 156 | 1.50 到 2.14 ms |
| 33 层住宅，二梯六户 | 420 | 420 | 3.65 到 4.79 ms |
| 33 层住宅，一梯四户 | 276 | 276 | 1.75 到 2.30 ms |

区间是连跑四次去掉最长一次之后的取值范围。耗时含造世界与跑完仿真两部分，由
`std::time::Instant` 量出，种子固定为 42。要一个更稳的数，得等 `benches/` 里那个
基准写出来。

## 3. 基准怎么跑

```
cargo bench                              全部
cargo bench --bench single_run           单次仿真
cargo bench --bench sweep                批量扫描吞吐
cargo bench --bench kinematics           运动学公式
cargo bench --bench dispatch             各替换点的决策开销
make bench-table                         重新生成 DISPATCH_API 里的对比表
```

基准用 criterion，结果落在 `target/criterion`。CI 里存历史曲线，性能倒退会报警。`benches/` 目录现在是空的，上面这些命令还没有对应的基准。

### 3.1 记录在案的信息

每次发布性能数字，必须同时记录：

```
commit 号
CPU 型号与核数
操作系统与 Rust 版本
构建的 profile，以及目标平台的特性开关
是否开启了超载死锁等可选行为
```

少了任何一项，那个数字都不可比。第 2.1 节这一轮数字与停靠时长等五个问题修复同一次提交，机器与 profile 同上，超载死锁按默认关闭。

## 4. 已知瓶颈在哪里

按预期的影响排序。**这是预测，落地之后要用火焰图验证，不成立就删掉这段。**

1. **随机数**。每秒要抽几百万次。手写 PCG32 纯整数实现，保持在个位数纳秒。循环里不许出现 trait 对象调用和外部库的函数链。
2. **Boarding 循环**。每次停靠对每个等待的人掷一次骰子，是热点。小规模热点可以考虑用定点整数代替浮点做概率比较，是否更快待验证。
3. **派梯估算**。`load_aware_eta` 这类算法要做前向推算，是二次热点。把每个场景中不变的部分缓存起来。
4. **事件堆**。元素数量只有几千，`log` 项不免费，但 `BinaryHeap` 的常数和可预测性需要实测。
5. **内存的局部性**。每层一个等待队列。单队列元素通常只有几十个，用固定容量的内联数组比堆容器更省。

## 5. 打算怎么加速

| 手段 | 适用层面 | 风险 |
| --- | --- | --- |
| 预分配，运行期零分配 | 全局 | 无 |
| 并行数组 layout 取代结构数组 | 热字段 | 代码变难读 |
| 泛型单体化取代动态派发 | 替换点 | 编译时间变长 |
| rayon 多线程 | 批量扫描 | WASM 环境不可用 |
| analytics 预筛 | 超大网格 | 多一套实现要维护 |

**analytics 预筛要谨慎加。** 用解析公式把明显没希望的组合先筛掉，听起来很美，但它引入了第二套逻辑。两套一旦不一致，给出的是错答案。至少要先有办法验证两者一致。也有可能不必加，先把原生速度做出来再说。

## 6. WASM 特别要量什么

### 6.1 实测

环境：Apple M4 Pro 14 核，macOS 15.7.5，rustc 1.89.0，Node v22.19.0，
`--profile release-wasm`。测量脚本是临时的，逻辑见下，不进仓库。体积一行用
`wc -c web/tihu.wasm` 与 `gzip -n -c web/tihu.wasm | wc -c` 量，单文件版量 `dist/tihu.html`。
`-n` 去掉 gzip 文件头里的时间戳，同一个产物重复量得到同一个字节数。
先用 `make wasm single` 出新产物。

| 项 | 数字 |
| --- | --- |
| WASM 产物 raw | 319,334 字节，311.9 KiB |
| WASM 产物 gzip | 112,905 字节，110.3 KiB |
| 单文件版 `dist/tihu.html` raw | 491,156 字节，479.6 KiB |
| 单文件版 gzip | 178,498 字节，174.3 KiB |
| `WebAssembly.instantiate` 耗时 | 中位 0.51 ms，20 次 |
| wasm 线性内存 | 1,179,648 字节，1.13 MiB |
| 单次调用，默认 18 层两梯 | 4.9 到 11.3 ms |
| 单次调用，33 层两梯六户 | 11.9 到 12.7 ms |
| 一次调用的响应体 | 5209 到 8973 字节 |
| 批量调用，1000 个种子，18 层两梯四户 | 中位 4409.7 ms，每次约 4.41 ms |
| 批量调用，1000 个种子，33 层两梯六户 | 中位 13326.2 ms，每次约 13.33 ms |
| 批量调用的响应体，18 层 | 6975 字节 |
| 批量调用的响应体，33 层 | 12287 字节 |
| 网页并行，64 个种子 | 中位 25 ms，7 次 |
| 网页并行，200 个种子 | 中位 93 ms，7 次 |
| 网页并行，200 个种子被顶掉后的那一轮 | 119 ms |

批量那次是种子 42 到 1041 共一千个，配置为预设 `std_residential` 与 `std_tall`，
走 `down_peak_sweep`，三次取中位。单次中位与批量每次耗时的差别来自固定开销：批量把造世界、
跨边界调用这类开销摊到一千次上，每次都便宜一点。响应体大了一截，逐层多了门到门的
均值、分位与最值，顶层结构没变。

单次耗时区间是默认的 `down_peak_sweep` 连跑多次的取值范围，上界含首次 JIT 预热的
那一趟。三种 Router 耗时同量级。早先集选明显更快，是空车趴窝不干活量出来的，已随
死锁修复消失。

第 2.2 节那条「网页端一次调用同步返回 100 ms 以内」的目标，实测最差 11.3 ms，
余量足够。这还没算浏览器的开销，但离 100 ms 有将近十倍的距离。

批量调用不在这条之内。一千个种子在三十三层同步要 13.3 秒，64 个种子起走 Web Worker
并行，见 [`ARCHITECTURE.md`](ARCHITECTURE.md) 第 8.3 节。

体积变小来自 `Cargo.toml` 的 `strip = true`。名字节与调试段落对运行没有用，去掉之后
raw 少 112,990 字节，降 26.1%，gzip 少 27,472 字节，降 19.6%。同一份改动让单文件版
raw 少 146,442 字节，降 23.0%，gzip 少 38,125 字节，降 17.6%。结果不变，
`tools/smoke.js` 的默认配置仍是送达 152 人、平均 28.5 秒、P90 63.3 秒。

网页并行那两行在浏览器里量，同一台机器同时开着旧版与新版两个页面，各连跑七次取中位。
旧版每轮新建八个工人再各发一份产物，64 个种子中位 36 毫秒，200 个种子 105 毫秒。
新版把池子留住只换种子区间，就是表里那两个数，64 个种子快 31%，200 个种子快 12%。
种子越多算得越久，省下的那份开销占比越小。被顶掉的那一轮要换一池新工人，
119 毫秒，比排队等旧分片算完划算，拖滑块时用户等的就是这一轮。
