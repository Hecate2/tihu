## 2. 为什么是 Rust

选型时比了三条路。

| 方案 | 网页端 | 海量扫描 | 结论 |
| --- | --- | --- | --- |
| Rust 内核加 WASM | 跑得快 | 原生多线程，最快 | **选中** |
| 纯 TypeScript | 免工具链 | 约为前者的五分之一，要靠 Worker 补 | 弃 |
| Python 加 Pyodide | 首屏几十 MB | 单进程，慢 | 弃 |

决定性的理由不是速度，是**不分叉**。网页和命令行编译的是同一个 crate。改了一个算式，两边同时生效。用两套语言重写一遍引擎，迟早会在「那个系数到底是 0.8 还是 0.85」这种地方闹鬼。

Rust 另外三个好处，正好对着本项目的需求：

- 无 GC。仿真跑几百万次循环，不能接受 STW 抖动。
- 数值仿真大量用索引访问数组。所有权系统把这些 unchecked 索引的风险压到最低，符合「最小化 `unsafe`」的约定。
- `Engine<Router, Assigner, Boarding>` 这种泛型参数天然适合做策略插拔，单体化之后零运行时开销。

需要付出的代价是：**wasm 目标和 `wasm-pack` 需要另外安装。** 装法写在 README。

## 3. 事件驱动引擎

时间是连续的，仿真按**事件驱动**推进，不按固定步长扫全场。

理由很直接。固定步长要么取 0.1 秒，那么一次 60 分钟仿真要跑 36000 步乘以全部对象。取粗一点也不行，门开关这种 2 秒级的过程会被抹平。事件驱动只在真正发生变化的时刻做计算。

### 3.1 事件种类

```
enum Event {
    CarStep(CarId),      // 轿厢状态机的下一个推进时刻
    Arrival(FloorId),    // 该楼层下一位乘客到达
    StallTick(CarId),    // 超载死锁的下一轮催促，默认关闭时不产生
}
```

堆里的元素数量是「轿厢数加楼层数」，几十个量级。`BinaryHeap` 带 `with_capacity` 预分配，运行期间不再申请内存。

### 3.2 主循环

```
loop {
    pop 最小时刻的事件
    clock = 该时刻
    match 事件 {
        Arrival(f)   => 生成同行团并入队 -> 触发一次派梯 -> 排下一次 Arrival
        CarStep(c)   => 推进该轿厢状态机一步 -> 得到 next -> 排下一次 CarStep
        StallTick(c) => 问一次有没有人愿意退出 -> 决定继续卡着还是恢复
    }
    到终止条件就退出
}
```

轿厢状态机：

```
Moving   -> 到达目标层 -> Opening
Opening  -> 开门完成   -> Boarding
Boarding -> 上下客循环 -> 没人可上了 -> Closing
Closing  -> 关门时判超载 -> 正常则 Moving / 超载则 Stalled
Stalled  -> StallTick 循环 -> Moving
Idle     -> 无任务，按 Router 的 idle 策略驻停或调度
```

关键点：**Boarding 是一个循环而不是一次性动作。** 有人在上客期间刚到电梯厅，他会趁着门还开着挤进来，这会把关门时刻往后推。循环条件是「还有人能上就继续」，收敛很快。不做这个循环会高估运力。

### 3.3 复杂度

```
事件总数 E ≈ 行程数 + 停靠次数 + 幽灵停站数
单次仿真 ≈ O(E · log(轿厢数 + 楼层数))
```

对三十四层四户的大楼，早高峰三千段行程，E 大约在两万到三万。**目标是把单跑压到 2 毫秒以内**，实测结果放 [`PERFORMANCE.md`](PERFORMANCE.md)，现在还是空的，跑出来才能填。

## 4. 内存布局

### 4.1 运行期间零分配

进入主循环之前，所有容器按配置推算的上界一次性 `with_capacity`，之后不再增长：

```
乘客数上界 = 楼层数 × 户数 × 户均人数 × 出行率 × 1.2
同行团上界 = 乘客数上界
每台轿厢在梯名单容量 = capacity_crush
每层等待队列容量 = 该层住户数上界
```

仿真进到循环里之后再也不 `malloc`。这条不仅是性能考虑，也让 profile 出来的火焰图干净，一眼能看出热点在哪。

### 4.2 结构体怎么放

乘客和同行团用 **arena 加索引**，不用 `Box`。一层 `Vec<Pax>` 加一层 `Vec<Party>`，互相引用用 `u32` 下标。

热路径上频繁读的字段，比如所在楼层、目的楼层、载重、拒挤度，考虑拆成并行数组。是否拆由基准数据决定，不预先优化。现在先把并行数组的接口位置留出来，等基准数据说话。

### 4.3 轿厢内的在梯名单

每位在梯乘客要能按目的楼层快速取出。轿厢规模小，一个记录 `Vec<PaxIdx>` 足够，几百字节。下车时线性扫一遍，容量最多十六个人，完全够用。

## 5. 随机性与公平比较

### 5.1 种子与流

随机数发生器手写 PCG32，纯整数运算，跨平台逐位一致。不依赖外部随机数库的默认发生器，因为它可能随版本变化。

根种子按用途派生出互不干扰的多条流：

| 流 | 抽什么 |
| --- | --- |
| 到达流 | 每位乘客到达电梯厅的时刻 |
| 目的层流 | 每位乘客要去哪一层 |
| 拒挤度流 | 每位乘客的拒挤度 |
| 体重流 | 每位乘客的体重 |
| 策略流 | 每位乘客采用哪种按键策略 |
| 拥挤检验流 | 每次停靠时谁愿意挤 |
| 时序噪声流 | 开关门与逗留时间的抖动 |

派生用 `splitmix64(seed, stream_id)`。

### 5.2 为什么必须分流

假设只有一条串行流。改动 `Router` 会改变每位乘客的经历，进而改变后续所有抽签的次序，于是**客流序列本身被挪位了**。两个算法表面上在比优劣，实际上在比两批不同的人。

分流之后，凡是描述乘客自身属性的随机量，全部在策略介入**之前**抽完：

```
关键顺序：先抽完所有乘客的到达时刻、目的层、拒挤度、体重，再开始跑第一帧
```

于是同一个种子下，无论配哪个算法，楼里都是同一批人。**这是公平比较的前提**，也是 `harness` 里 A/B 测试的默认方式。

仍然会分流之后变动的只有「运行期的行为抽签」，比如某次停靠时谁愿意挤。这类抽签受策略影响，是允许的，我们正是要观察这种差别。

## 6. 三个可插拔的替换点

细节见 [`DISPATCH_API.md`](DISPATCH_API.md)。这里只写架构约束。

| 替换点 | 决定什么 | 每次仿真被调用几次 |
| --- | --- | --- |
| `Assigner` | 新外呼派给哪台轿厢 | 每个外呼一次，加上重分配回调 |
| `Router` | 轿厢往哪走、停不停 | 每到达一层一次 |
| `Boarding` | 谁有权上车、什么时刻关门 | 每次停靠若干次 |

### 6.1 泛型单体化

```
pub struct Engine<R: Router, A: Assigner, B: Boarding> { ... }
```

内建算法走这条路，三个 `dyn` 都不用。这符合仓库「最小化 `dyn`」的约定，也让编译器能把整个状态机内联展开。

### 6.2 `Box<dyn>` 逃生舱

算法的选择要留到运行时才决定，或者由外部动态载入时，提供下面这条路径：

```
type DynRouter = Box<dyn Router>;
```

代价是每次决策多一次动态派发，实测数字由基准补齐。**逃生舱是可选路径，不是唯一路径。** 任何人提交「为了方便统一改成 dyn」的补丁都应该被否决。

### 6.3 注册表

```
registry(registry_id) -> impl Router
```

网页下拉框、命令行 `--router` 参数，都从同一张表里读。加一个新算法只要在这张表加一行，不需要改动别的文件。

## 7. WASM 边界

### 7.1 传什么

跨边界只传两样东西：一份 JSON 配置进去，一份 JSON 结果出来。

```
SimConfig (serde_json) -> WASM -> ResultBundle (serde_json)
```

原因是**仿真过程本身不跨界**。一次调用在 WASM 内部跑完几千段行程，只把聚合结果传出来。逐乘客地跨境传递会有几十倍的开销，没有任何必要。

### 7.2 热路径不解析 JSON

只有函数的出入口用 JSON。引擎内部全部是原生结构体。这条区别很重要，早期原型容易为了省事一路 `serde_json::Value` 往下传，快不了。

批量调用走这条路。一次传 N 份配置和 N 个种子，WASM 内部循环跑完，一次性返回 N 份结果。网页要做三十个參數点扫描时就用这个接口，避免三十次跨边界调用。

### 7.3 初始化

```
await WebAssembly.instantiateStreaming(fetch('tihu_core_bg.wasm'), imports)  // 走 network
```

单文件版在 `file://` 下没有 fetch 权限，改成 base64 内嵌加 `WebAssembly.compile(bytes)`。**这是「双击就能玩」能成立的技术前提**，README 里承诺的那一点靠它实现。

## 8. 网页前端

### 8.1 没有框架

原生 JavaScript，一个 `app.js` 加一个 `charts.js`。理由：

- 产物小，毕竟只有几十 KB 的业务代码
- 零外部依赖，断网可用，没有 CDN 挂掉的风险
- 静态形态符合「便于部署」

图表全部手写 SVG。柱线图、直方图、热力图加起来不到三百行。引一个 Chart.js 的体积比业务代码本身还大，不划算。

### 8.2 状态与 URL

```
state = 全部输入参数的一个对象
```

任何一次变更把 state 序列化进 URL 的 hash。用户可以复制链接，把「33 层、二梯六户、三分之一的人反向叫梯」这样一份完整配置发给别人。这个功能配合预设按钮使用。

### 8.3 卡顿怎么处理

单次调用是同步的，跑几十次而已，浏览器会卡几十毫秒，可接受。做大批次扫描时分片执行，每片之间 `requestAnimationFrame` 让出主线程，同时画进度条。

**网页定位是「几百次运行」，不是「十万级」。** 十万级请回到命令行。

## 9. 命令行与批量扫描

```
tihu-cli run      单次运行，打印人类可读报告
tihu-cli sweep    参数网格扫描，输出 CSV 或 Parquet
tihu-cli bench    跑标准测试套件，对比各调度算法
tihu-cli evolve   多日演化
tihu-cli nash     二分找策略比例的临界点
tihu-cli validate 只校验参数合法性，不跑仿真
tihu-cli calibrate 接现场掐表数据反推参数（P6）
```

### 9.1 并行

网格在最外层展开成任务列表，交给 rayon 的线程池，每个任务内部用各自的本地缓冲。结果经一个 channel 汇总写盘，避免把一百万行堆在内存里。

### 9.2 断点续跑

已完成的参数组合写入一个 sidecar 文件。中断之后重跑同一个命令自动跳过。跑几小时的任务非常需要这个。

### 9.3 输出

CSV 一行一个组合，列包括全部输入参数加全部输出指标，可以直接丢给 pandas 或者任何表格软件。Parquet 作为可选输出。
