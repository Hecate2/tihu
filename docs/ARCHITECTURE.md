## 2. 为什么是 Rust

选型时比了三条路。

| 方案 | 网页端 | 海量扫描 | 结论 |
| --- | --- | --- | --- |
| Rust 内核加 WASM | 跑得快 | 原生多线程，最快 | **选中** |
| 纯 TypeScript | 免工具链 | 约为前者的五分之一，要靠 Worker 补 | 弃 |
| Python 加 Pyodide | 首屏几十 MB | 单进程，慢 | 弃 |

决定性的理由不是速度，是不分叉。网页和命令行编译的是同一个 crate。改了一个算式，两边同时生效。用两套语言重写一遍引擎，迟早会在「那个系数到底是 0.8 还是 0.85」这种地方闹鬼。

Rust 另外三个好处，正好对着本项目的需求：

- 无 GC。仿真跑几百万次循环，不能接受 STW 抖动。
- 数值仿真大量用索引访问数组。所有权系统把这些 unchecked 索引的风险压到最低，符合「最小化 `unsafe`」的约定。
- `run<R: Router, A: Assigner, B: Boarding>` 这种泛型参数天然适合做策略插拔，单体化之后零运行时开销。

需要付出的代价是：**wasm 目标和 `wasm-pack` 需要另外安装。** 装法写在 README。

## 3. 事件驱动引擎

时间是连续的，仿真按**事件驱动**推进，不按固定步长扫全场。

理由很直接。固定步长要么取 0.1 秒，那么一次 60 分钟仿真要跑 36000 步乘以全部对象。取粗一点也不行，门开关这种 2 秒级的过程会被抹平。事件驱动只在真正发生变化的时刻做计算。

### 3.1 事件种类

```
enum Kind {
    CarStep(CarId),      // 轿厢状态机推进一层，或者走完一次停靠
    Arrive(usize),       // 某位乘客走到电梯厅了
    Abandon(usize),      // 某位乘客等得不耐烦，改走楼梯
    StallTick(CarId),    // 超载死锁的下一轮催促，默认关闭时不产生
}
```

`Arrive` 带的是乘客下标，不是楼层。堆里的元素数量是「轿厢数加乘客数」，几千个量级。`BinaryHeap` 带 `with_capacity` 预分配，运行期间不再申请内存。

### 3.2 内核决定停不停

一条腿指「轿厢从某个楼层一次赶往目标层」的一段行程。轿厢沿这条腿逐层推进，每到一层由内核判断该不该停。判据只有两条：

1. 车上有乘客要在这一层下
2. 这一层在本车这条腿的预定停靠表 `stops_planned` 里

开一条腿时，内核把名下的同向外呼和车上乘客的目的层填进停靠表。目标层上的外呼不论朝向都排进来，那是这台车这趟的折返点。折返点不收人，车就会在「到了却不停」和「返回本层」之间空转。

外呼在途中被指派给一台已经在移动的车时，内核先做一次制动可行性检查，剩余距离够刹停才插进去，来不及就记一次越站。见 [`MODEL.md`](MODEL.md) 第 3.8 节。

**停靠决策归内核，`Router` 只回答「下一程去哪」。** 这条分工让算法无论怎么写，都不会「路过该停的层」，也不会「停在没活可干的层」。因此 `Router` 的方法只剩 `next_leg`。

### 3.3 主循环

```
loop {
    pop 最小时刻的事件
    clock = 该时刻
    match 事件 {
        Arrive(pid)  => 进出该层电梯厅 -> 登记外呼 -> 派梯一次
        Abandon(pid) => 从电梯厅退场，改走楼梯，计入另一类统计
        CarStep(c)   => 推进该轿厢状态机一步 -> 重算归属 -> 排下一次 CarStep
        StallTick(c) => 问一次有没有人愿意退出 -> 决定继续卡着还是恢复
    }
    到终止条件就退出
}
```

轿厢状态机：

```
Idle     -> 本层有人要下，或者本层名下有活且有人等 -> Boarding
         -> 否则按 Router 选下一程，目标不是本层 -> Moving
Moving   -> 到达该停的层 -> Boarding
         -> 到了目标层却已经没活可干 -> Idle
Boarding -> 关门时刻到 -> Idle
Stalled  -> StallTick 循环 -> Idle
```

关键点：**Boarding 是一个循环而不是一次性动作。** 上客反复扫整段队列，队首挤不上时后面的人仍有机会上，直到一整轮没人能上为止。不做这个循环会高估运力。关门时刻在停靠开始时就按开关门时序算定，停靠期间新到的人不会被算进来。

### 3.4 复杂度

```
事件总数 E ≈ 乘客到达数 + 弃梯数 + 行程段数 + 停靠次数 + 幽灵停站数
单次仿真 ≈ O(E · log(轿厢数 + 乘客数))
```

对三十三层六户的大楼，早高峰乘客三百多人，事件数几千。实测单跑在毫秒量级，见 [`PERFORMANCE.md`](PERFORMANCE.md) 第 2.1 节。

## 4. 内存布局

### 4.1 运行期间零分配

进入主循环之前，事件堆与各容器按配置推算的上界一次性 `with_capacity`，之后不再增长：

```
乘客数上界 = 楼层数 × 户数 × 户均人数 × 出行率 × 1.2
每台轿厢在梯名单容量 = capacity_crush
每层电梯厅容量 = 该层住户数上界
```

仿真进到循环里之后再也不 `malloc`。这条不仅是性能考虑，也让 profile 出来的火焰图干净，一眼能看出热点在哪。

### 4.2 视图靠复用缓冲

三个替换点拿到的是只读视图。视图里的切片直接借用内核一块复用的 `Scratch` 缓冲，构造视图不分配内存。`RunView` 的 `car_calls` 与 `mine` 两个切片，以及 `SystemView` 的 `cars`、`pending` 等都是这么来的。算法可以放心在热路径上反复调用。

内选楼层不单独存。早先有一个 `Car::car_calls` 字段，但从来没人往里写，于是 `will_alight` 对算法永远回答 false。现在由在梯乘客的目的层现算，构造视图时排好序填进去。

### 4.3 结构体怎么放

乘客放在一层 `Vec<Pax>` 里，互相引用用下标。轿厢放在 `Vec<Car>` 里。热路径上频繁读的字段就在结构体里顺序排，暂不拆并行数组，等基准数据再说。

### 4.4 轿厢内的在梯名单与电梯厅

`Car::occupants: Vec<usize>` 记录在梯乘客的下标。轿厢规模小，容量最多十几个人，放出时线性扫一遍完全够用。

每层电梯厅是一个 `Vec<Vec<usize>>`，下标是楼层格位，存此刻在等的人。不做预排序，进出都是常数级操作。

## 5. 随机性与公平比较

### 5.1 种子与流

随机数发生器手写 PCG32，纯整数运算，跨平台逐位一致。不依赖外部随机数库的默认发生器，因为它可能随版本变化。

根种子按用途派生出互不干扰的十条流：

| 流 | 编号 | 抽什么 |
| --- | --- | --- |
| 到达流 | `Arrival` | 每位乘客到达电梯厅的时刻，以及团内抖动 |
| 目的层流 | `Destination` | 每位乘客的目的层，反向细流的抽签 |
| 拒挤度流 | `Tolerance` | 每位乘客的拒挤度 |
| 体重流 | `Weight` | 每位乘客的体重 |
| 策略流 | `Strategy` | 每位乘客采用哪种按键策略，以及带不带小孩 |
| 拥挤检验流 | `Squeeze` | 每次停靠时谁愿意挤 |
| 时序噪声流 | `Timing` | 开关门与逗留时间的抖动 |
| 需求流 | `Demand` | 是否出门、是否返程、走不走楼梯 |
| 僵局流 | `Stall` | 超载僵持时谁愿意退出 |
| 耐心流 | `Patience` | 每位乘客愿意等多久才改走楼梯 |

派生用 `splitmix64(seed, stream_id)`。`Stream` 枚举把这十条编号固定下来，`Stream::ALL` 供自检遍历。

### 5.2 为什么必须分流

假设只有一条串行流。改动 `Router` 会改变每位乘客的经历，进而改变后续所有抽签的次序，于是**客流序列本身被挪位了**。两个算法表面上在比优劣，实际上是在比两批不同的人。

分流之后，凡是描述乘客自身属性的随机量，全部在策略介入**之前**抽完：

```
关键顺序：先抽完所有乘客的到达时刻、目的层、拒挤度、体重，再开始跑第一帧
```

于是同一个种子下，无论配哪个算法，楼里都是同一批人。**这是公平比较的前提**，也是 `harness` 里 A/B 测试的默认方式。

仍然会分流之后变动的只有「运行期的行为抽签」，比如某次停靠时谁愿意挤、僵局里谁先退出。这类抽签受策略影响，是允许的，我们正是要观察这种差别。

### 5.3 统计检验

发生器本身要过一组统计检验，写成会失败的单元测试：

- `next_u32` 切 16 个桶做卡方检验
- `below` 取模采样在几个不规整的模数上做卡方检验
- 相邻两次抽签的序列相关系数接近 0
- `next_u32` 的 0 与 1 位数均衡
- 根种子派生出的各条流互不撞车
- `splitmix64` 的输出高位分布均匀

## 6. 三个可插拔的替换点

细节见 [`DISPATCH_API.md`](DISPATCH_API.md)。这里只写架构约束。

| 替换点 | 决定什么 | 每次仿真被调用几次 |
| --- | --- | --- |
| `Assigner` | 新外呼派给哪台轿厢 | 每个外呼一次，后面每个事件还调一次重分配 |
| `Router` | 轿厢下一程去哪 | 轿厢每次重新决策时一次 |
| `Boarding` | 谁有权上车、什么时刻关门 | 每次停靠每位候选乘客一次 |

### 6.1 Router 的新签名

`should_stop` 和 `idle` 两个方法连同 `Idle` 枚举已经删掉。停靠决策收回内核，算法不用再回答「这一层停不停」。现在的签名只剩一个决策方法：

```rust
pub trait Router {
    fn name(&self) -> &'static str;
    fn next_leg(&self, v: &RunView<'_>) -> Leg;
    fn reset(&mut self) {}
}
```

`Assigner` 保留 `assign` 与 `reassign`，`Boarding` 保留 `admit_one` 与 `close_now`。三者互不耦合。研究者只想改走向，就只写 `Router`，不用碰另外两个。

### 6.2 泛型单体化

三个点都是泛型参数，内建算法一个 `dyn` 都不用：

```rust
pub fn run<R: Router, A: Assigner, B: Boarding>(
    cfg: Config,
    router: &mut R,
    assigner: &mut A,
    boarding: &B,
) -> Run
```

这符合仓库「最小化 `dyn`」的约定，也让编译器能把整个状态机内联展开。

### 6.3 `Box<dyn>` 逃生舱

算法的选择要留到运行时才决定，或者由外部动态载入时，本可以走下面这条路径：

```rust
type DynRouter = Box<dyn Router>;
```

代价是每次决策多一次动态派发。**逃生舱是可选路径，不是唯一路径。** 任何人提交「为了方便统一改成 dyn」的补丁都应该被否决。这条路径现在还没接上，三个替换点目前只能是编译期泛型参数。

### 6.4 注册表

网页下拉框与命令行 `--router` 参数将来从同一张表里读选。这张表目前只有 `builtin.rs` 里的一份内建实现清单，按名字在运行时选用还没接上。加一个新算法就加一个类型，不需要改动内核的其他地方。

## 7. WASM 边界

### 7.1 传什么

跨边界只传两样东西：一份 JSON 配置进去，一份 JSON 结果出来。

```
SimConfig (serde_json) -> WASM -> ResultBundle (serde_json)
```

原因是**仿真过程本身不跨界**。一次调用在 WASM 内部跑完几千段行程，只把聚合结果传出来。逐乘客地跨境传递会有几十倍的开销，没有任何必要。

### 7.2 热路径不解析 JSON

只有函数的出入口用 JSON。引擎内部全部是原生结构体。这条区别很重要，早期原型容易为了省事一路 `serde_json::Value` 往下传，快不了。

批量调用走这条路。**种子范围写在配置里**，网页给一个起始种子与一个结束种子，
WASM 内部依次跑完中间每个种子再汇总，一次性返回一份聚合报告，不用为每个种子
跨一次边界。聚合的累加器在 `tihu-core/src/batch.rs`，只与楼层数有关，与种子
个数无关。上限见 `config.rs` 的 `MAX_SEEDS`。

### 7.3 初始化

```
await WebAssembly.instantiateStreaming(fetch('tihu_core_bg.wasm'), imports)  // 走 network
```

单文件版在 `file://` 下没有 fetch 权限，改成 base64 内嵌加 `WebAssembly.compile(bytes)`。**这是「双击就能玩」能成立的技术前提**，README 里承诺的那一点靠它实现。

## 8. 网页前端

### 8.1 没有框架

原生 JavaScript，`app.js` 管控件与调用，`charts.js` 管 SVG 图表，
`merge.js` 管分片报告合并，`worker.js` 是并行池的工人。理由：

- 产物小，毕竟只有几十 KB 的业务代码
- 零外部依赖，断网可用，没有 CDN 挂掉的风险
- 静态形态符合「便于部署」

图表全部手写 SVG。柱线图、直方图、热力图加起来不到三百行。引一个 Chart.js 的体积比业务代码本身还大，不划算。

### 8.2 状态与 URL

```
state = 全部输入参数的一个对象
```

任何一次变更把 state 序列化进 URL 的 hash。用户可以复制链接，把「33 层、二梯六户、三分之一的人反向叫梯」这样一份完整配置发给别人。这个功能配合预设按钮使用。

### 8.3 卡顿与并行怎么处理

单次调用是同步的，跑几毫秒，浏览器卡一下可接受。多种子批量分两条路，
按种子数切，阈值见 `web/app.js` 的 `PARALLEL_MIN_RUNS`（64 个）：

- 少量种子走同一次同步调用，内核在内部循环，网页只等一份聚合报告。
- 64 个种子起把范围切成几段，每个 Web Worker 各带一份 WASM 实例算一段，
  主线程按 `web/merge.js` 合成一份报告。合并口径对照内核 `batch.rs`，
  与一次跑完相比小数部分差 0.001 以内，个数类字段在半数边界上可能差 1。
  node 以真实产物实测三组配置乘三组算法，见 `tools/verify-merge.js`。

工人起不来就回退同步，保证旧环境照样出数。种子范围仍卡在 1000，
见 `crates/tihu-core/src/config.rs` 的 `MAX_SEEDS`。

单文件版把 `worker.js` 以纯文本内嵌，`file://` 下以 Blob 启动，不用联网。
静态服务器下按 `worker.js` 文件名拿。浏览器里的实际加速比待实测，
`<!-- TODO -->`：补 `file://` 与 http 下 1000 种子的并行耗时。

**网页定位是「几百次运行」，不是十万级。** 十万级请回到命令行。

## 9. 命令行与批量扫描

```
tihu-cli run      单次运行，打印人类可读报告
tihu-cli sweep    参数网格扫描，输出 CSV 或 Parquet
tihu-cli bench    跑标准测试套件，对比各调度算法
tihu-cli evolve   多日演化
tihu-cli nash     二分找策略比例的临界点
tihu-cli validate 只校验参数合法性，不跑仿真
tihu-cli calibrate 接现场掐表数据反推参数（P6）
```

### 9.1 并行

网格在最外层展开成任务列表，交给 rayon 的线程池，每个任务内部用各自的本地缓冲。结果经一个 channel 汇总写盘，避免把一百万行堆在内存里。

### 9.2 断点续跑

已完成的参数组合写入一个 sidecar 文件。中断之后重跑同一个命令自动跳过。跑几小时的任务非常需要这个。

### 9.3 输出

CSV 一行一个组合，列包括全部输入参数加全部输出指标，可以直接丢给 pandas 或者任何表格软件。Parquet 作为可选输出。
