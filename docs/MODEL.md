# 仿真模型说明 MODEL

这份文档写的是**模型语义**：每个参数代表什么、为什么是这个默认值、相邻行为怎么判。想知道代码怎么分层，看 [`ARCHITECTURE.md`](ARCHITECTURE.md)。想知道怎么插一个调度算法，看 [`DISPATCH_API.md`](DISPATCH_API.md)。

文中所有标 `待标定` 的常数，都意味着「目前是行业经验值，还没在本仓库里被实测校准」。按 [`../AGENTS.md`](../AGENTS.md) 第 2.3 条，这类常数的代码位置都挂着 `TODO(calibration)`。

## 1. 仿真世界由什么组成

一次仿真里有三类东西：

| 东西 | 数量级 | 说明 |
| --- | --- | --- |
| 轿厢 `Car` | 2 到 8 台 | 一个状态机，见第 3 节 |
| 外呼 `HallCall` | 每层最多 2 个 | 上行呼叫与下行呼叫，按 `(楼层, 方向)` 去重 |
| 乘客 `Pax` | 数百到数千 | 带一到两条行程腿，见第 4 节 |

同一户的人到达时刻只差几十秒，模型里当半个同行团看。上下客现在按人头逐个判定，还没有把整户当成一个不可拆的单位。

**时间是连续的**，单位为秒。仿真按事件驱动推进，不按固定步长一遍遍扫全场。每一步只在真正发生变化的时刻做计算，见 [`ARCHITECTURE.md`](ARCHITECTURE.md) 第 3 节。每层电梯厅的等待队列不预先排序，哪一层此刻有谁在等，由到达事件逐个填进去。

## 2. 建筑模型与密度约束

### 2.1 楼层是怎么编号的

**层号 1 是主入口层**，就是住户进出大楼的那一层。地上共 N 层的住宅，层号就是 1 到 N，最高层号就是 N。地下层用负数，B1 是 -1，B2 是 -2。层号 0 不存在。

所以「18 层住宅」的 `top_level` 就是 18，工具里存的最高层号就是地上层数，不额外加主入口层。填 18 得到 1 到 18 共 18 层。预设 `std_residential` 用 `top_level = 18`，`std_tall` 用 33，`stress_mixed_traffic` 与 `hospital` 都是 24 层。

`Building` 里两个字段跟着这套编号走：

| 字段 | 含义 |
| --- | --- |
| `top_level` | 最高层号，类型 `i16`。它就是地上层数 |
| `units_per_floor` | 逐层户数表，下标等于层号减一，长度必须等于 `top_level` |

户数表下标 0 的那一格是主入口层。`ground_floor_residential` 默认 `true`，主入口层默认也住人。关掉它就变成架空层、大堂或者商铺，预设楼盘的一层也住人。三个助手函数负责层号换算，`lowest_level()` 给出有地下层时的最低层号，`highest_level()` 给出最高层号，`n_levels()` 给出楼层格位总数。

### 2.2 自由的量和不自由的量

层数、每层户数、每户人数这三个数不能随便给。它们被楼板面积约束住。

```
第 f 层的住户数 = 户数(f) × 户均人数(f)
```

两条硬约束：

```
户数(f)  ≤  floor( 该层套内面积 / 最小套型面积 )
户数(f) × 户均人数(f)  ≤  floor( 该层套内面积 / 人均最低面积 )
```

再加一条常识上限：单户人数不超过 6。

### 2.3 两种输入方式

**方式 A，直接给**（网页默认）。用户直接填层数、户数、户均人数。内核跑一遍上面的不等式，产出两种结果之一：

- 违反硬约束 → `error`，网页直接不让运行，并把「至少要多大的楼板面积才塞得下这么多人」算出来给用户看
- 逼近硬约束 → `warn`，网页显示一条黄条：「按 20 m²/人 反推，这样配置已经接近规范下限，实际楼盘不太可能存在」

**方式 B，由户型推导**。用户给每层建筑面积和一个户型表，例如 `[90, 90, 120, 140]`，内核反推户数，以及更接近现实的户均人数：

```
户数        = 户型表的长度
户均人数(u) = clamp( round(套型面积 / 面积每人), 1, 6 )
```

`面积每人` 默认值 **26 m²/人**，待标定。这条只是一个估算手法，真实户型的居住人数和面积相关，但关系远非线性。

### 2.4 每层的特殊情形

给一个逐层覆盖向量，支持三种特殊情形：

- 一层不住人，改成架空层、大堂、商铺。由 `ground_floor_residential` 控制。全局默认住人，预设楼盘的一层也住人
- 顶层跃层，户数减半，由 `top_floor_duplex` 控制
- 有无地下室，由 `basement_levels` 控制，默认为 0。有的话，早高峰有一部分人意外的目的地是车库而不是大堂

### 2.5 默认值

| 参数 | 默认 | 出处 |
| --- | --- | --- |
| 层高 | 3.0 m | 住宅常见 2.8 到 3.1 |
| 每层户数 | 4 | 用户调 |
| 户均人数 | 2.8 | 七普家庭户平均规模约 2.62 人。**待标定**：住户不等于家庭户，这里要复核 |
| 最小套型面积 | 45 m² | 待标定，需对照《住宅设计规范》条文 |
| 人均最低面积 | 20 m² | 待标定 |
| 单户人数上限 | 6 | 常识约束 |

### 2.6 轿厢停靠区域

真实楼盘常把梯群分区。一部只停单层，一部只停双层，或者高低区分开。模型里每台轿厢带一个 `StopSpec`：

| 写法 | 停哪些层 |
| --- | --- |
| `StopSpec::All` | 全部楼层。默认 |
| `StopSpec::list([1, 5, 9])` | 显式枚举的楼层 |
| `StopSpec::parity(true)` | 奇数层。主入口层与地下层一律停 |
| `StopSpec::parity(false)` | 偶数层。主入口层与地下层一律停 |
| `StopSpec::zone(1, 15)` | `[lo, hi]` 闭区间 |
| `StopSpec::union(parts)` | 上面若干条的并集 |

单双层那两种写法自动把层号 `<= 1` 的层包含进来，也就是主入口层加所有地下层。不这样做，地下车库会没有一台车愿意去。

每台轿厢还可以指定初始停在哪一层，字段是 `initial_level`，默认停在主入口层 1。

内核在两处强制这条约束。派梯时，算法如果点了一台不停该层的车，内核换成一台真正服务的车顶上。上客时，乘客只能登上同时停靠出发层与目的层的轿厢。少了这一条，分区梯上的乘客会被拉上车却到不了自己的楼层。

配置校验拦下两类错误。`unserved_floor` 表示某一层没有任何轿厢停靠。`no_through_car` 表示某个住了人的楼层，没有一台轿厢同时停靠这一层与主入口层。层号 0 不存在，校验时跳过。

## 3. 轿厢运动学

这一节负责把「从第 3 层到第 27 层」算成具体的秒数。

### 3.1 上下行各有一套运动曲线

上行和下行不必对称。真实电梯两个方向的极限速度、加速度、减速度、加加速度都可能不同，模型把它们拆成两套装参数。

```
struct MotionProfile {
    v_max: f32,   // 该方向的极限速度, m/s
    a_acc: f32,   // 起步加速度, m/s^2
    a_dec: f32,   // 停车减速度, m/s^2
    j_acc: f32,   // 起步加加速度, m/s^3
    j_dec: f32,   // 停车加加速度, m/s^3
}
```

六个量都能单独设置。默认走上下对称的常见设定。

| 参数 | 默认 | 出处 |
| --- | --- | --- |
| `v_max` 上行 | 1.75 m/s | 住宅主流配置 |
| `v_max` 下行 | 取上行同值 | 多数电梯两向一致。改成不同值可以模拟下行限速的旧梯 |
| `a_acc` 上行 | 0.80 m/s² | 待标定 |
| `a_dec` 上行 | 0.80 m/s² | 待标定 |
| `a_acc` 下行 | 0.80 m/s² | 待标定 |
| `a_dec` 下行 | 0.80 m/s² | 待标定 |
| `j_acc` | 1.00 m/s³ | 待标定 |
| `j_dec` | 1.00 m/s³ | 待标定 |

**这条要如实说清。** 实现里的速度剖面是一条线性斜坡，速度从 0 线性升到峰值速度，再线性降到 0。加加速度项只表现为一个时间补偿量。它不是真 S 曲线，是工程级的简化模型，别拿它做驱动控制设计。位置与速度的口径自洽，本节三处的公式互相对得上，也各配一条单元测试。

### 3.2 走一段距离要多久

以下用某一方向的那一组参数，简称 `a_acc`、`a_dec`、`j_acc`、`j_dec`，行程距离记为 `L`。

加速段与减速段：

```
t_acc(v) = v/a_acc + a_acc/j_acc
d_acc(v) = v²/(2·a_acc) + v·a_acc/(2·j_acc)
t_dec(v) = v/a_dec + a_dec/j_dec
d_dec(v) = v²/(2·a_dec) + v·a_dec/(2·j_dec)
```

第一问是行程够不够长到能跑满 `v_max`。

**够长**，条件是 `L ≥ d_acc(v_max) + d_dec(v_max)`：

```
t = t_acc(v_max) + t_dec(v_max) + (L − d_acc(v_max) − d_dec(v_max)) / v_max
```

**不够长**，就跑不到 `v_max`。峰值速度 `v_p` 从 `d_acc(v_p) + d_dec(v_p) = L` 解出：

```
A   = 1/(2·a_acc) + 1/(2·a_dec)
B   = a_acc/(2·j_acc) + a_dec/(2·j_dec)
v_p = ( −B + √(B² + 4·A·L) ) / (2·A)
t   = t_acc(v_p) + t_dec(v_p)
```

上下对称时这一组式子退化成更简单的形式，退化关系本身是一条单元测试。

### 3.3 算一遍看看

取层高 3.0 m，上下都用 `v_max = 1.75`、`a = 0.8`、`j = 1.0`，跑相邻单层：

```
d_acc + d_dec = 1.75²/0.8 + 1.75×0.8/1.0 = 3.83 + 1.40 = 5.23 m  >  3.0 m
```

跑不到额定速度，走第二支：

```
A   = 1/(2×0.8) + 1/(2×0.8) = 1.25
B   = 0.8/(2×1.0) + 0.8/(2×1.0) = 0.80
v_p = (−0.80 + √(0.64 + 4×1.25×3.0)) / (2×1.25) = 1.262 m/s
t   = 2 × (1.262/0.8 + 0.8/1.0) = 4.75 s
```

相邻单层 4.75 秒。这个数是后面所有结论的锚点，所以算式全部展开写在这里。

> 这一节第一版在草稿里手算得到 4.60 秒，错在解二次方程时系数漏乘。上面的数字由本节的公式用脚本实算得出，可以直接复跑。教训记在这里：凡是手算的步骤一律脚本复核。

### 3.4 一个反直觉的结论

固定加速度和加加速度时，只要行程短到跑不满额定速度，峰值速度就由行程长度决定，和额定值无关。于是存在一个阈值：额定速度超过它之后，单层时间就不再下降。

| 层高 | 额定速度超过这个值，单层时间锁死 |
| --- | --- |
| 2.8 m | 1.210 m/s |
| 3.0 m | 1.262 m/s |
| 3.3 m | 1.336 m/s |

层高 3.0 m 时，额定 1.5、1.75、2.5、3.0 m/s 的单层运行时间全部相同，都是 4.75 秒。差别只出现在长距离上。同一栋楼从底层跑到 30 层也就是 90 m：

| 额定速度 | 90 m 行程耗时 |
| --- | --- |
| 1.75 m/s | 54.42 s |
| 2.5 m/s | 39.33 s |
| 3.0 m/s | 33.77 s |

2.5 m/s 相对 1.75 m/s，长距离省 15 秒，单层省 0 秒。买高层多花的那笔钱到底买到了什么，这是一个能把话说清楚的角度。

讲这段时必须带上下面这句提醒。现实里高速电梯的驱动调校也不同，加速度和加加速度都会更大，所以实际单层时间仍有差别，见下一节的预设表。

### 3.5 预设档位

不同速度档的典型驱动参数并不相同。预设表如下，加速度与加加速度一律待标定。

| 预设名 | 额定速度 | 加速度 | 加加速度 | 单层 3.0 m | 跑 30 层 90 m |
| --- | --- | --- | --- | --- | --- |
| `low_rise_1_0` | 1.0 m/s | 0.50 m/s² | 0.60 m/s³ | 5.83 s | 92.83 s |
| `std_1_6` | 1.6 m/s | 0.65 m/s² | 0.80 m/s³ | 5.19 s | 59.52 s |
| `std_1_75` | 1.75 m/s | 0.80 m/s² | 1.00 m/s³ | 4.75 s | 54.42 s |
| `high_2_5` | 2.5 m/s | 1.00 m/s² | 1.20 m/s³ | 4.40 s | 39.33 s |
| `high_3_0` | 3.0 m/s | 1.00 m/s² | 1.30 m/s³ | 4.32 s | 33.77 s |

表中数值由 3.2 的公式算出，目前由单元测试固定。`benches/` 还是空的，跑 `cargo bench kinematics` 复现这件事还没做。

设上下不对称时的例子。同样是 90 m 行程，上行按 2.5 m/s、下行按 2.0 m/s：

```
上行 39.93 s    下行 48.30 s    相差 8.38 s
```

### 3.6 停一次站白花多少时间

`stop_overhead` 是一次停靠在运行时间之外额外付出的时间：

```
stop_overhead = (开门 − 提前开门补偿) + 保持开启 + 关门 + 控制器响应
```

启停的加减速损耗不在这里算，因为它已经包含在运动曲线里了。重复计一次是最容易犯的错。

| 参数 | 默认 | 出处 |
| --- | --- | --- |
| 开门 | 2.0 s | 中分门，行业通行取值，待标定 |
| 提前开门补偿 | 0.5 s | 平层前预开门，待标定 |
| 保持开启 | 1.5 s | 待标定 |
| 关门 | 2.8 s | 含光幕确认，待标定 |
| 控制器响应 | 0.2 s | 待标定 |

默认合计 6.0 秒。另外两个参数用来算上下客时间。每人进梯 1.0 秒，每人出梯 0.8 秒，两者同时进行时取较大者再乘 0.35 的重叠折扣。这几个数一律待标定。

加上 3.3 的 4.75 秒，可以粗算一笔：某趟跑到第 3 层停一次，单单「跑到加停一次再加跑开」就是 4.75 + 6.0 + 4.75 ≈ 15.5 秒起步。一趟经过十几次停靠的行程，时间大半花在门上，不花在路上。

### 3.7 层高的影响

层高每多 0.1 m，单层多用大约 0.07 秒：

| 层高 | 单层时间（额定 1.75 m/s，a=0.8，j=1.0） |
| --- | --- |
| 2.8 m | 4.63 s |
| 2.9 m | 4.69 s |
| 3.0 m | 4.75 s |
| 3.1 m | 4.82 s |
| 3.3 m | 4.94 s |

单层看不出来，但一栋 33 层楼的整趟行程会把这点差别累加起来。

### 3.8 制动距离与越站

`motion` 模块对外给出三个几何量。`decel_distance(v)` 是从速度 `v` 刹到停所需的距离。`state_at(dist, t)` 给出走 `dist` 米时时刻 `t` 已经走过的距离和当时的速度。`time_at_distance(dist, d)` 反过来，给出走过 `d` 米所对应的时刻。逐层推进和制动判断都用它们。

一条外呼在途中被指派给一台已经在移动的轿厢时，内核先做一次制动可行性检查。判据是剩余距离不小于 `decel_distance(v) + v × 0.3s`。0.3 秒是控制器从接到指令到开始减速的滞后，待标定，代码里的常数名是 `BRAKE_REACTION_S`。来不及刹停，这台车就照直开过那一层，`Car::overshoots` 加一。

后果按速度档自然分化。高速梯制动距离长，接下来连续好几层都停不了。低速梯几乎不会漏掉任何一层。哪一层住户的体验更好，这里能算出来。

## 4. 客流模型

### 4.1 客流模式

| 模式 | 主目的地方向 | 说明 |
| --- | --- | --- |
| `morning_down` | 住宅层 → 主入口层 | 早高峰，绝大多数人往外走 |
| `evening_up` | 主入口层 → 住宅层 | 晚高峰，绝大多数人回家 |
| `noon_mixed` | 双向 | 中午，两向都有，强度低 |
| `inter_floor` | 由 `flows` 指定 | 层间交通。医院、写字楼这类大部分行程发生在楼层之间的场景 |

`inter_floor` 模式下，客流由 `traffic.flows` 逐股给出，每一股写明起点、终点与
占比。占比不必归一化。

```toml
pattern = "inter_floor"
flows = [
  { from = 3,  to = 12, share = 0.30 },   # 门诊去手术层
  { from = 12, to = 2,  share = 0.25 },   # 手术层送回门诊
  { from = 6,  to = 20, share = 0.25 },   # 检验去住院病区
]
```

这个模式下 `units_per_floor` 读作「每层几个科室或病房」，`persons_per_unit` 读作
「每间常驻几人」。总的团数按全楼住户乘出行率估出，再按占比摊到各股上。

校验会拦住三种写法：没有给客流表、占比为负、某一股的起终点没有一台车同时停靠。
预设 `hospital` 是一个现成的例子。

晚高峰以前只生成住宅层出发的人，这是一个错误，已经修掉。现在晚高峰的主流从主入口层上楼回家，另有一小撮人下楼。中午两向各掷一次，各占一半。

### 4.2 强度曲线

高峰窗口 `[t0, t0+T]`，`T` 默认 60 分钟。窗口内的出行强度用贝塔型钟形：

```
φ(s) ∝ s^(α−1) · (1−s)^(β−1),   s ∈ (0,1)
```

默认 `α = β = 2.5`，单峰，峰位在正中。峰的强度偏前或偏后通过调整两个参数实现。

出行率 `departure_ratio` 是「窗口内有多大比例的住户离家」，默认 **0.66**。

### 4.3 逐层生成

逐户生成。每户按 `departure_ratio` 掷一次，中了就出一趟。出发时刻从钟形强度曲线上抽，峰值落在窗口中段。

目的地只有两个去处。绝大多数去主入口层。有地下层时，7% 的人直接下到车库，具体下 B1 还是 B2 随机。7% 是行业估法，待标定，代码里挂在 `pick_exit` 与 `pick_entrance` 上。

反向细流按户掷，命中概率是 `reverse_ratio`，默认 0.08。这里用伯努利抽签，不按户数乘比例取整。小楼里那一撮人一旦取整就会被抹成零。待标定。

同楼其他楼层之间串门这种目的地还没有做，挂 `TODO(calibration)`。

### 4.4 同行团怎么形成

一家三口早上一起出门，他们不会拆开上两趟梯。模型里按户聚合，一户生成一个团。

团里各人的到达时刻只差几十秒，用到达流在 0 到 90 秒之间抽一个抖动。团人数取户均人数四舍五入再封顶 4 人，从户均人数涌现出来，不单独指定。带小孩的团占 `child_party_ratio` 比例，默认 0.35，早高峰要送小孩上学，待标定。

团人数上限和不可拆分性质都会直接影响第 5 节里「车没坐满就开走了」的结果。

`party_window_s` 这个参数目前没有消费者。合并是在生成时按户一次性完成的，还没有按到达时间窗动态并团。

### 4.5 行程腿与条件性返程

每位乘客带一到两条行程腿，一条腿的格式是 `Hop { from, to }`。腿数记在 `n_hops`，当前走到第几条记在 `hop_idx`。

只带一条腿的人出门就到目的地。带两条腿的人先到某一层，原地停 `dwell_s`，再从那一层返回。第二条腿的进场事件在运行时排，时刻等于上一腿的出梯时刻加 `dwell_s`。所以条件性返程不需要提前知道，也不用提前决定。

`return_ratio` 决定出门的人里有多大比例会返程，默认 **0.005**，待标定。`return_dwell_s` 是停留时长中位数，默认 **900 秒**，待标定。停留时长按对数正态抽，变异系数 0.5，下限 30 秒。

真实场景对应的是下到车库拿个东西再上楼，送孩子到楼下再回家。全部随机量在乘客生成时一次性抽完，所以同一份种子跑两次，返程行为完全一致。

### 4.6 等不下去改走楼梯

每位乘客带一个 `patience_s`，从对数正态抽，中位数是 `abandon_after_s`，默认 **1200 秒**。变异系数是 `abandon_cv`，默认 **0.45**。两个数待标定。

到达时刻加上 `patience_s` 会排一个 `Abandon` 事件。到了那一刻他还没上车，就改走楼梯，从电梯厅退场，指标里单独记成 `abandoned`。`abandon_after_s = 0` 或者 `stairs.enabled = false` 都会关掉这条机制，那时谁的 `patience_s` 都是无穷大。

中途弃梯的人确实等过，那段等待时间算进等待分布。不算进去的话，报告里的平均等待会被系统性低估，因为等最久的那批人正好是从统计里消失的那批。

**弃梯受可行层数约束。** 这一趟跨度超过 `practical_floor_cap` 的人不许弃梯，只能
继续等。现实中没人会爬二十层楼梯去上班，让模型里出现这种动作会算出一批本来
不存在的「已送达」。这一条与 7.2 节那个上限是同一个参数，语义也一样：一个是
出发前就没人愿意走，一个是半路想走也走不了。

## 5. 呼叫、登梯、以及挤不上

### 5.1 一次按键只叫来一台轿厢

这是本仓库**最容易写错的一条**，写错会让高峰期结果完全失真。

外呼以 `(楼层, 方向)` 为键存在注册表里。规则：

```
register(floor, direction):
    若该键已点亮:
        什么都不发生，只把等待人数 +1
    否则:
        新建一条未分配的外呼，交给 Assigner 派给某一台轿厢
```

同层同方向的第二个人按下按钮，灯是亮的，不会再召来第二台车。**其余轿厢不响应这条呼叫。**

对照之下，「每个排队的人各派一台车」的朴素写法会把高峰期等待时间算得很乐观，因为系统凭空多出了几倍的运力。

### 5.2 有人会多按

两种多按行为，分别对应两种现实场景。

**上下都按**。住低楼层的人等下行等不到，把上行也按下。这条同时产生两个效应：他自己可能先搭上一趟上行车再折返下来，以及那个上行呼叫大概率变成一次无人上车的幽灵停站。

**呼叫多台**。这只存在两种情形。一是走廊里每个轿厢各有自己的按钮面板，人可以对着两台车各按一次。二是并联群控，但人把两边走廊的按钮都按了。参数 `call_surface` 取值：

| 取值 | 行为 |
| --- | --- |
| `group_single` | 并联群控共用一套上下按钮，一次按键一个外呼。**住宅默认值** |
| `per_car_panel` | 每台轿厢独立按钮，乘客可以指定轿厢，也可以同时呼叫多台 |

多按的人占多大比例由策略向量控制，见第 6 节。

### 5.3 幽灵停站

乘客召唤了 k 台轿厢，最终只上了一台。剩下 k−1 台的呼叫在他上车之后不会消失，系统会照着服务。

后果是某台轿厢抵达那层，开门，没人进，关门，掉头走人。一次白花的 `stop_overhead` 加上绕路的运行时间。这就是**幽灵停站**，指标名是 `ghost_stops`。

有人负责的呼叫一律保留。现实里按键灯亮着，轿厢一定会来，到了才发现没人上，那一次停靠就是幽灵停站。这条判据正是红线 2 的落点。

### 5.4 谁可以上车

轿厢到站开门后，先下后上。上客在一个时刻内反复扫整段队列，直到一整轮没人能上为止。队首那位挤不上时，后面的人仍有机会上车，这是真实电梯的样子。

一位乘客要满足三条才上得去：

```
1. 他的目的方向与轿厢这一层收人的方向一致，或者轿厢停着不动
2. 这台轿厢同时停靠他的出发层与目的层
3. 剩余空间够，且他个人的拒挤判定通过
```

第 2 条是分区梯的落点。收人方向按名下的外呼定，车在折返点时按反方向收人，见 [`ARCHITECTURE.md`](ARCHITECTURE.md) 第 3 节。

关门时刻在停靠开始时就按开关门时序算定。停靠期间新到的人不会被算进这一次。这条口径在 `docs/GPU.md` 的缺漏清单里记着。

### 5.5 挤梯判据

这是业主明确提的一条：**接近满载时，上不去是随机的，而且车会在没坐满的情况下开走。**

#### 5.5.1 容量线

| 名字 | 默认 | 含义 |
| --- | --- | --- |
| `capacity_rated` C | 由额定载重除以 75 kg 推出 | 铭牌上的额定载客人数 |
| `soft_start` r₀ | 0.75 × C | 低于这条线，人人都上，不掷骰子 |
| `capacity_crush` C_max | 1.25 × C，向上取整 | 人数上限。超出这个数，再怎么挤也挤不进去 |
| `load_crush` W_max | 1.10 × 额定载重 | 载重上限，千克。超出这个重量就再也进不来人 |

**人数与千克各管一头。** 乘客站在电梯厅里只能看到里面挤了几个人，看不到总重量，
所以「愿不愿意挤」这条心理判据一路按人数走，见下一节。轿厢本身受的是载重约束，
所以「还装不装得下」按千克判。两个上限取先到的那个，都记 `no_space`。

载重上限默认取额定的 1.10 倍，比 1.05 倍的报警线高。这个先后次序是有意的：人
先挤到报警线，轿厢才开始僵持。反过来设的话，重量上限会先把人挡在外面，超载
报警永远等不到。

#### 5.5.2 拒绝概率

载客率超过 `soft_start` 之后，每位乘客各掷一次。载客率越接近 1，拒绝的概率越高。

```
ρ = clamp( (load/C − r₀) / (1 − r₀), 0, 1 ) ^ γ
```

个人属性 `tol_i ∈ [0,1]` 是这位乘客的**拒挤度**，生成时从贝塔分布抽一次，终身不变。`tol = 0` 是沙丁鱼爱好者，`tol = 1` 是绝不肯贴着人站的那类。

等得越久越能将就。加一个焦躁补偿：

```
w = min( waited / wait_ref, 1 ) × β_焦躁
p_上车 = clamp( 1 − tol_i × ρ + w, 0, 1 )
```

默认 `γ = 1.0`，`wait_ref = 120 s`，`β_焦躁 = 0.4`。三者待标定。

三个效应的合力是这样的：同样的拥挤程度，等了三分钟的人和刚到 20 秒的人，做出的决定不一样。这个差别是建模的关键，也是「拒挤」这个词的含义所在。

#### 5.5.3 为什么这样就可能出现「没坐满就开走」

原因有两个，都合理：

1. **掷骰子被拒**。还剩 2 个位子，队首三人各有六成概率放弃，谁都没上时车就开走了。
2. **有人去不了**。他的目的层这台车不停，或者方向对不上，他只能留下，车带着空位开走。

记一次 `partial_departures` 的条件是：有人上来过，车厢却没装满，层上还有人等。

#### 5.5.4 由此产生的两类记录

`no_space` 表示真的没位子了，`declined` 表示有位子但被拒绝。**这两个必须分开统计**，混成一个数会让「这个楼盘是不是运力不够」的判断失真：前者要加电梯，后者不用。

### 5.6 满载直驶与顺手接走

**满载直驶。** 轿厢满员时，路过的同向外呼不再停靠，直接开过去，`Car::full_bypasses` 加一。判据是车里人数到了 `capacity_rated`、这一层没人要下、且这一层有一条本车方向上还亮着的外呼。少了这条机制，满载车会照样停靠开门，没人上得去，白记成幽灵停站。

**顺手接走。** 共享外呼只归一台轿厢。等待者的目的层若超出归属车的停靠范围，归属车送不了他，他也没有第二张外呼。这时任何一台停在该层、又送得了他的轿厢都该接走。到站的空车不再按残留的车头方向挑人，见 `sim.rs` 的 `waiting_rescue` 与 `board_dir_at`。

归属车揽着一条自己送不了的外呼时，不能原地反复开门。它会卡在停靠与决策之间，一层的高层等待者一个也上不去，这正是分区梯曾静默丢人的原因。停机判据是 `Car::settled_level`。

## 6. 内卷策略

### 6.1 策略表

`StrategyMix` 给四种策略各配一个比例，归一化后使用。默认全员 `honest`。

| 策略 | 按键行为 | 上车后行为 |
| --- | --- | --- |
| `honest` | 按真实方向 | 直达目的地 |
| `press_both` | 上下都按 | 哪趟先来上哪趟 |
| `press_up_only` | 只按上行 | 只按上行等待 |
| `multi_call` | 同时呼叫多台 | 搭最先到的那台，其余台变成幽灵停站 |

`multi_call` 只在 `per_car_panel` 下真的叫多台，且固定叫两台。其余情况它退化成一次普通呼叫。策略比例是外部输入，模型不会自己决定住户按不按。预设 `stress_gaming` 用 0.7 诚实、0.25 上下都按、0.05 只按上行。

### 6.2 转向层

反向叫梯者登上上行车之后，需要一个目的层。转向层的取法按早期设计是取该趟行程里其他乘客的最高目的层，或者轿厢当前最高内选。

代码里 `reversal_floor` 记下了他上车的层，但还没有真正按它约束行程。反向叫梯者应该一路坐到折返点再下来，现在靠路由自然带过去。这条在 `docs/GPU.md` 的缺漏清单里记着。

**这里正是悲剧所在。** 对个人来说这笔账常常是划算的，因为他争取到的是别人根本看不上的一趟空车。对全楼来说，每台被占用来做无用功的轿厢都在挤压别人的运力。

### 6.3 逐日演化

多日模式每一天结束后，算各策略的平均门到门时间，然后按复制者动态更新比例：

```
fitness_i  = 1 / (1 + T_i)      或    −T_i 的单调映射
x_i'       = x_i · fitness_i / Σ x_j · fitness_j
```

加一个下限 `ε = 0.01`，避免某个策略彻底灭绝之后再也无法复活。完全灭绝会让原本有趣的复苏现象被漏掉。

典型产出是一条逐渐恶化的曲线：第一天 5% 的人耍赖占了便宜，第五天变成 40%，第三周全楼都学会了反向叫梯，而**所有人的出行时间都比第一天更长**。

**这一段目前还没写。** `Sim::days` 与 `Sim::evolution_epsilon` 两个开关留在配置里，代码里还没有消费者。

### 6.4 临界点

固定比例扫描模式下，对着比例做二分，找使 `T_honest ≈ T_gamer` 的那个点。这个点就是 tipping point。跨过它之后，理性的下一步是跟风，然后大家一起变差。

实现要求：二分时必须用**同一批种子的客流**，否则方向差异会被客流噪声淹没。见 `ARCHITECTURE.md` 第 5 节「公共随机数」。这一功能还没有写。

## 7. 走楼梯

### 7.1 出门前就定下走不走

走楼梯在这里是一个行为模型。住户不会做「电梯全程耗时与爬楼全程耗时」这种全局比较，他们凭日常经验：两三楼的邻居天天爬，八楼以上的人想都不会想。所以意愿按层数衰减，再乘上「电梯比楼梯快不了多少」这个事实。

```
T_楼梯(f)  = 每层下行秒数 × f + 每层费力惩罚 × f + 固定开销
意愿(f)     = base_willingness × (1 − decay_per_floor × f)
胜算        = logistic( (T_电梯估计 − T_楼梯) / τ )
P(走楼梯)   = 意愿 × 胜算
```

层数超过 `practical_floor_cap` 之后，意愿只剩原来的百分之二，留给电梯慢得离谱的那种情形。

`T_电梯估计` 是乘客脑子里的先验信念，不是仿真算出来的真实值。它由几个常数粗估：一轮往返耗时、层高带来的加成、轿厢数按平方根打折。估得太乐观会让高层住户算出爬楼划算，那是错的。所以这段估计刻意往悲观里取。

### 7.2 默认值与校准目标

| 参数 | 默认 | 出处 |
| --- | --- | --- |
| 每层下行秒数 | 4.5 s | 3.0 m 层高，步行速度约 1.0 m/s 加每层一个平台转身的时间。待标定 |
| 每层费力惩罚 | 2.5 s | 把「爬楼很烦、膝盖疼」折算成的秒数。待标定 |
| 固定开销 | 5 s | 走到楼梯间的时间。待标定 |
| 判定噪声 τ | 45 s | 人对几十秒的差异才敏感。待标定 |
| 上行费力乘数 | 3.0 | 往上爬比往下走难受得多。待标定 |
| `base_willingness` | 0.24 | 一层楼的住户有多大可能走楼梯。待标定 |
| `decay_per_floor` | 0.055 | 意愿随层数的相对衰减。待标定 |
| `practical_floor_cap` | 6 | 六层以上基本没人走，同时是弃梯的可行层数上限。待标定 |
| `abandon_after_s` | 1200 s | 弃梯的中位等待时长，见 4.6。待标定 |
| `abandon_cv` | 0.45 | 耐心阈值的变异系数。待标定 |

三层住户的下楼成本是这条模型的锚点：

```
T_楼梯(2 层) = 2×4.5 + 2×2.5 + 5 = 19 s
```

高峰期等电梯再加坐到主入口层，常常超过 60 秒，所以三到五层会有零星几个人走楼梯。**十层以上基本没人走**，因为光是下行加费力就超过 70 秒，再叠加判定噪声，实际概率落在个位数百分比以下。

`base_willingness` 取 0.24 是调出来的，原先取 0.31 时比例偏高。它让全楼走楼梯的比例落进下面的目标区间。

**默认值必须被实测校准。** 校准目标：正常运行下全楼走楼梯的人数占比落在 **2% 到 5%**，并且集中在 2 到 6 层。这条写成一条验收测试，判据是 `stair_share ∈ [0.02, 0.05]`，只数出发前就决定走楼梯的那些人。

### 7.3 上行也可以走楼梯

早高峰下行是主场景。晚高峰上行也允许走楼梯，但往上爬的费力乘数要高得多，默认下来占比接近零。

### 7.4 一个反直觉的效应

走楼梯的人抬走了轿厢系统的一部分负载，**留下来坐电梯的人反而等得短一些**。这个效应很小，但要在报告里写出来，因为它意味着「楼里有多少人愿意爬楼梯」本身是影响结论的参数。

## 8. 超载死锁

**默认关闭。** 因为它极其罕见，开着会把日常结论淹没。开关名字是 `overload.enabled`，默认 `false`。

### 8.1 什么时候会发生

超载判据看的是**重量**，与挤梯那套人数判据分开。

```
过载判据 = Σ 轿厢内每位乘客的体重 > 额定载重 × trigger_ratio
```

体重在乘客生成时抽一次，终身不变，折返走第二条腿时也不重抽。分布是可配置的
多分量对数正态混合 `WeightMix`，默认四个峰：

| 分量 | 占比 | 中位数，公斤 | 变异系数 |
| --- | --- | --- | --- |
| 成年男性 | 0.38 | 68 | 0.15 |
| 成年女性 | 0.36 | 56 | 0.15 |
| 小孩 | 0.18 | 26 | 0.22 |
| 很重的人 | 0.06 | 105 | 0.18 |

另外每个人加一份 `carried_kg`，默认 **2.5 公斤**，代表衣物与随身物品。占比与
中位数都待标定。

出处：中国居民营养与慢性病状况报告给出成年男性平均体重约 69.6 公斤，女性约
58.1 公斤。对数正态的中位数略低于均值，所以这里取 68 与 56。**具体年份与分布
形态待核。**

用混合而不是单一分布，是因为真人不是一个峰。分开之后，既能抽出一撮很重的人，
也能把小孩的比例压到合理范围。带小孩的同行团里，尾部那几位强制走小孩峰，
相关性保住。

### 8.2 为什么额定 13 人还能超载

额定人数按 **75 kg/人** 折算，这是行业常规。真人的平均体重远低于 75。所以：

```
1000 kg 轿厢 → 额定 13 人 → 13 位乘客的混合均值约 61 kg → 13 × 61 ≈ 793 kg
```

793 公斤离 1050 公斤的报警线还差一大截。额定 13 人真正被压过去的路径只有一条：
**人挤到了远超额定数的程度**。

真正把人逼到那里的是「候梯人数远超运载能力」这个前提。**业主要求的因果链条在这里闭合**：超需求运行 → 拒挤度被焦躁压低 → 塞到物理极限 → 重量越过报警线 → 死锁。

载重上限设在 1.10 倍，报警线在 1.05 倍，两者都低于 1.25 倍的人数上限。这个次序
保证报警一定发生在「装不下」之前，僵局才有机会形成。

| 参数 | 默认 | 出处 |
| --- | --- | --- |
| `trigger_ratio` | 1.05 | 超载保护装置动作值。**待标定**，需对照安全规范条文 |
| `crush_factor` | 1.25 | 人数上限相对额定人数的倍数。待标定 |
| `crush_load_ratio` | 1.10 | 载重上限相对额定载重的倍数。待标定 |

### 8.3 死锁怎么解开

报警触发后轿厢进入 `Stalled` 状态。门开着，蜂鸣器响，**不再接受任何上车**。

每过一轮 `stall_tick_s` 考察一次有没有人愿意退出：

```
最后上车的人退出概率 = q_last       默认 0.35
其他人每人的退出概率 = q_other      默认 0.05
每累积 30 秒，两者都乘以 stress_growth，默认 1.6
```

出场顺序从最后上车的人开始往前挨个问。退出的人保留原始到达时刻重新排队，
等待时间接着累计，不算一次新的等待，但要打一个 `requeued_after_stall` 标记。

**被请下车的人不是「已到达」。** 他从轿厢里出来，一步都没往目的地走，所以这一腿
的状态要清空，人会回到出发层的电梯厅重新排队，并重新获得一个完整的耐心窗口。
把他直接记成到达，行程会被算成完成，等待时间的口径也会跟着乱。

`stall_timeout_s` 兜底，默认 **300 秒**。超过这个时间按人口最接近门口的人强制退出，并在日志里记一条。

### 8.4 它为什么是调度算法的试金石

这里正是业主前面提的那条「一个按钮只叫一台轿厢」和最坏情形交汇的地方。

轿厢卡死之后，它名下那条已经登记的外呼通常是**没有别的轿厢会去接的**。因为派梯关系是早先建立的，系统认为这件事已经有人负责了。层上的人发现按钮灯是亮的，再按一次没反应，灯也不会因为多按而变成两次请求。

差别就在这里：

| Assigner | 卡死时的表现 |
| --- | --- |
| 派出去就不管 | 这一层的人一直等到卡车自己恢复为止，中间不会有任何第二台车过来 |
| 支持呼叫重分配 | 检测到卡车超过某时长未推进，把未服务的外呼改派给别的轿厢 |

后者的平均恢复时间可能只是前者的一个零头。**同一个场景之下，两个算法会在这里拉开巨大差距**，这也是 `docs/PLAN.md` 的标准测试套件里要专门放一个「轿厢长时间停滞」专项场景的原因。

### 8.5 由此产生的指标

| 指标 | 含义 |
| --- | --- |
| `stalls` | 死锁次数 |
| `stall_seconds` | 死锁累计秒数 |
| `pax_after_stall` | 因僵局被赶出轿厢、随后重新排队的乘客数 |
| `calls_orphaned` | 因轿厢停滞而无人接管的外呼数。代码里还没接上，目前恒为 0 |

单次最长死锁 `stall_max` 还没记。

## 9. 输出指标

时间类指标在每位乘客每次到站时逐腿累加，不做最后一遍全量扫描。带返程的乘客两条腿各记一次。

### 9.1 乘客视角

| 指标 | 定义 |
| --- | --- |
| `wait` | 到电梯厅的时刻到进去轿厢的时刻 |
| `ride` | 进去轿厢到出轿厢 |
| `door_to_door` | `wait` 加 `ride`。反向叫梯者的这一项包含绕行 |
| `bypass_count` | 到站没上去的次数 |
| `pax_any_bypass` | 至少被跳过一次的人占完成行程人数的比例 |
| `pax_bypass3_frac` | 被跳过三次以上的人占的比例 |

分位数用直方图存，每格 0.5 秒，另配一个溢出桶。理由是三条：跨线程可合并、内存固定、尾部问题分析起来方便。

### 9.2 楼层视角

`by_floor` 按楼层格位铺开，下标等于层号加地下层数，覆盖包括地下层与主入口层在内的每一层。每层给出出发人数、等待均值、等待最大值、等待直方图、门到门均值、门到门最大值、门到门直方图、被跳过次数、`no_space` 与 `declined` 的各自计数、这一层走楼梯的人数。门到门只记真正坐上车走完的人，中途弃梯的只进等待不进门到门，分母是坐上车的人数。

这是给买房人看的最重要一张表。同一栋楼里，9 层和 25 层的体验往往会差出一大截。

### 9.3 系统视角

| 指标 | 定义 |
| --- | --- |
| `pax_total` | 全部乘客数，含走楼梯的 |
| `pax_served` | 走完至少一条腿、且没走楼梯也没弃梯的乘客数 |
| `stair_users` | 出发前决定走楼梯、以及中途弃梯的人数之和 |
| `abandoned` | 中途弃梯的人数，单独计量 |
| `throughput_5min` | 5 分钟输送人数，按完成行程人数折算，用于对照运力是否够 |
| `rtt_mean` | 实测平均往返时间，代理口径见第 10 节 |
| `trips` | 完成的往返趟数 |
| `ghost_stops` | 幽灵停站次数 |
| `partial_departures` | 未满载就发车、而层上还有人等的停靠次数 |
| `overshoots` | 因制动来不及而跳过的外呼层次数 |
| `stalls` | 超载死锁次数，默认关闭时为 0 |
| `stall_seconds` | 超载死锁累计秒数 |
| `calls_orphaned` | 占位字段，还没接上，目前恒为 0 |
| `full_bypasses` | 满载直驶次数。轿厢满员时路过一条还亮着的同向外呼却没停，记一次。见第 5.6 节 |

## 10. 拿解析公式校验

### 10.1 上行高峰往返时间

上行高峰期一台轿厢跑完一圈的时间，解析形式如下：

```
RTT = 2·H·t_v + (S+1)·t_s + 2·P·t_p
```

其中 `H` 是最高折返楼层到主入口层的行程，`t_v` 是单位行程时间，`S` 是期望停靠次数，`t_s` 是单次停靠开销，`P` 是单趟平均乘客数，`t_p` 是单人进出时间。

期望停靠次数在 `N` 个可能被服务的楼层、`P` 名乘客时：

```
S = N · ( 1 − (1 − 1/N)^P )
```

### 10.2 什么时候这两个数应该对得上

在下列全部成立时，仿真实测的 `rtt_mean` 应该落在解析值附近：

- 只有一个高峰方向，反向客流关掉
- 所有人的策略设为 `honest`，超载死锁关掉
- 挤梯判据关掉，也就是不存在拒绝上车
- 乘客数远低于轿厢容量，也就是「一趟装得下所有人」

这四个条件全部满足时，仿真退化成一个教科书问题。**对不上就说明事件循环或者运动学写错了**，这是一条非常好用的回归防线。这条对照测试目前还没接上。容差待标定，先取 10%。

### 10.3 实现在用的 RTT 口径是一个代理

仿真实测的 `rtt_mean` 用的是「空车出发到空车返回」的口径。一台车空着开始接第一段活时记下起点，车上清空、并且真的有人下过车时收尾。中间夹着的空驶和折返都算进去。

它和 10.1 的解析式不是一回事。解析式按整圈上行高峰算，代理口径把每一条接人腿都算进去。对照时看趋势与量级，别指望两个数相等。将来接上 10.2 的校验时，要专门处理这个口径差。

### 10.4 这套校验不能代替实测

解析公式只在理想条件下成立。真实世界的信心来自另一条路：`tihu-cli calibrate` 接一组现场掐表数据，反推模型里的参数。见 `docs/PLAN.md` 的 P6。

## 11. 已知的模型边界

写清楚，免得被人拿去做不该做的事。

1. **不建模某一厂家的专属群控算法**。真实厂家的算法闭源且有专利。本仓库的内建算法都是公开可查的经典做法，目的是给出一个合理基线，不是复现某一款产品。
2. **不建模消防安全疏散、担架梯、消防员运行**。
3. **不建模抱闸、钢丝绳曳引、能耗**。需要算电费请找别的工具。
4. **不建模一栋楼多个单元各自的梯群**。`entrances` 这个参数可以做排列组合，但第一版不实现。
5. **不建模住户错峰习惯的长期形成**。`departure_ratio` 和窗口宽度是外部输入，模型不会自己决定人们几点出门。
6. **不建模轿厢内的站立位置与走动路线**。上下客只按时序算时间，不还原空间。
