# 实施路线 PLAN

**当前状态：内核与网页第一版都能跑，命令行仍是空壳。**

内核 `tihu-core` 含测试约六千行，运动学、事件循环、停靠语义、客流、停靠区域、随机流、指标都在。`tihu-wasm` 用手写 ABI 把内核包成静态网页，`web/` 四个文件无框架无依赖，`make single` 产出可双击的单文件版。命令行、基准、验收脚本仍是空壳，演化与临界点二分、现场校准都还没做。

本文件按 phase 切。每个 phase 一个提交，scope 要紧，提交前 `cargo test` 全绿。很小的后续修正用 `git commit --amend` 并进去，不要一直叠新的提交。

验收有两条硬线：

1. `docs/MODEL.md` 里的六条建模红线，每一条都要有**会失败的测试**兜着
2. 任何没有跑过的数字不许写进文档

## P4.5 单层长队列

**状态：已完成。**

**问题。** 晚高峰上行，需求全部集中在主入口层，那里始终只有一条外呼。一条外呼在任一
时刻只挂在一台轿厢名下，其余轿厢停在原地不参与分担。修之前实测三十三层六户，台数从
两台加到六台，晚高峰平均等梯只从 903.9 秒降到 871.8 秒，六台车里三四台各自只跑三五趟
空驶。同一栋楼早高峰从 157.9 秒降到 46.1 秒表示加车本来是有用的。

**改法。** 两条配合。

1. 归属车到达某层收尾后，不许原地再开一次门。不拦的话，车主揽着一条自己送不了的
   外呼会反复空停靠，`choose_leg` 永远走不到，整台车卡死，同一层的高层等待者一个也
   上不去。判据是 `Car.settled_level`，见 `sim.rs` 的 Idle 分支。
2. 外呼仍只登记一条，归属车也仍只一台。但只要层上还有归属车送不了的等待者，任何一台
   停在该层、又送得了他的车都顺手接走，见 `waiting_rescue`。到站的空车不再按残留的
   车头方向收人，见 `board_dir_at`。新来的这类等待者会叫醒停在同层的闲车。

**实测。** 三十三层六户，晚高峰平均等梯两台 440.0 秒、三台 226.5 秒、四台 167.4 秒、
六台 132.4 秒，六台对两台改善七成。早高峰对应 142.8 降到 46.9 秒。全表见
[`SIMULATE.md`](SIMULATE.md) 第 6 节。

**验收**

- [x] 晚高峰上行加车，平均等梯随台数单调下降，六台对两台的改善不低于三成
- [x] 红线 1 的两条测试仍然全绿
- [x] 同一种子逐位可复现
- [x] 回归测试 `zoned_cars_pick_up_each_others_unservable_waiters`

## 之后的候选

这一节不是承诺，是留位。每条都要先回答「它能不能改变买房决策或者调度算法排名」。

- 大件物品进电梯，比如电动车和装修材料，这是超载的真实诱因之一
- 多个单元各自的梯群，而不是一栋楼一个大群
- 中间层分区或单双层停站策略。`StopSpec` 已经支持，还缺一个默认预设
- 待机层的优化配置
- 逐日的乘客学习 effect，也就是住户根据昨天的体验调整出门时间
