# 实施路线 PLAN

**当前状态：P0 之前，一行实现代码都还没有。**

本文件按 phase 切。每个 phase 一个提交，scope 要紧，提交前 `cargo test` 全绿。很小的后续修正用 `git commit --amend` 并进去，不要一直叠新的提交。

验收有两条硬线：

1. `docs/MODEL.md` 里的六条建模红线，每一条都要有**会失败的测试**兜着
2. 任何没有跑过的数字不许写进文档

---

## P0 骨架与运动学

**目标**：把 workspace 立起来，先把「第 3 层到第 27 层多少秒」这件事算对。

**交付物**

- `tihu-core`、`tihu-cli`、`tihu-wasm` 三个 crate
- `config` 模块：全部参数的结构体，含 serde 派生
- `motion` 模块：上下行两套 `MotionProfile`，见 MODEL.md 第 3.1 与 3.2 节
- `Makefile` 与 CI 配置

**验收**

- [ ] 运动学对照 MODEL.md 3.3 的展开算式，单元测试逐项比
- [ ] 上下对称时退化简单形式，这条退化关系本身是一条测试
- [ ] `docs/MODEL.md` 第 3.4 与 3.5 两张表的数字，跑 `cargo bench kinematics` 能复现
- [ ] 密度约束的校验函数就位（红线 5）
- [ ] `cargo build --workspace --all-targets` 干净通过

---

## P1 单台轿厢与第一批数字

**目标**：一台轿厢跑一趟完整的高峰，命令行能打印出第一个可信的平均等待时间。

**交付物**

- `car` 状态机，含 BOARDING 循环
- `traffic` 客流生成器，非齐次泊松，见 MODEL.md 第 4 节
- `engine` 事件主循环
- `tihu-cli run`
- 基本的 `metrics` 累加器

**验收**

- [ ] 解析往返时间对照通过，容差 10%，见 MODEL.md 第 10 节
- [ ] 客流生成器的泊松性质过拟合检验
- [ ] 跑 `docs/PERFORMANCE.md` 的 `REF` 场景，把单跑耗时填进 PERFORMANCE 第 2 节
- [ ] 同一份种子连跑两次，结果逐位一致

---

## P2 呼叫语义与调度插拔

**目标**：多台轿厢并联。这一步建立呼叫语义与调度插拔，**红线 1 在这里落地，并且之后不许再丢**。

**交付物**

- 外呼注册表，按 `(楼层, 方向)` 去重
- 三个替换点 trait：`Assigner`、`Router`、`Boarding`
- 注册表 `registry`，命令行的 `--router` 与网页下拉框共用
- 内建实现：`nearest_car`、`round_robin`、`collective_scan`、`selective_collective`
- 幽灵停站的产生与统计

**验收**

- [ ] 二十个人在同一楼层排同一个方向，**只产生一条外呼，只派出一台轿厢**。这是红线 1 的测试
- [ ] 幽灵停站的计数和时长都被统计出来，红线 2
- [ ] 写一个新 Router 可以在 100 行内完成且不用改内核，按 DISPATCH_API 的例子实测一遍
- [ ] 动态派发与泛型单体化的路径各有一份基准，数字进 PERFORMANCE

---

## P3 挤得上与走楼梯

**目标**：把「挤满上不去」和「低楼层有人爬楼梯」落进来。

**交付物**

- 三条容量线与拒挤度判定，见 MODEL.md 第 5.5 节
- 同行团的形成与不可拆分性质，见 MODEL.md 第 4.4 节
- 走楼梯决策，见 MODEL.md 第 7 节
- 两类挤不上的原因分开统计：`no_space` 与 `declined`

**验收**

- [ ] 存在「轿厢没坐满就开走」的停靠，且这种现象被单独计量，红线 3
- [ ] 开启走楼梯时，`stair_share_total` 落在 2% 到 5%，红线 4
- [ ] 走楼梯的人集中在 2 到 6 层，十层以上接近零
- [ ] 关掉走楼梯选项时快路径生效，结果和旧版本一致

## P4 网页第一版

**目标**：非技术用户打开浏览器就能玩。

**交付物**

- `tihu-wasm` 绑定与批量调用接口
- `web/` 的四个文件，无框架无依赖
- 手写 SVG 的三个大字与四张图
- URL hash 存配置，预设按钮
- `make single` 产出可双击的单文件版

**验收**

- [ ] 网页与 CLI 同一参数同一份种子，结果一致到 1e-9
- [ ] 断网状态下 `dist/tihu.html` 双击可用
- [ ] 一次调用的开销不超过目标值 100 ms，数字进 PERFORMANCE
- [ ] WASM 产物体积进 PERFORMANCE 第 6 节

---

## P5 行为层

**目标**：把那些「极其罕见但很要命」的行为做进去，默认全部关闭。

**交付物**

- 反向叫梯与转向层逻辑，见 MODEL.md 第 6 节
- 多呼叫行为与它的幽灵停站放大效应
- 超载死锁：体重模型、报警判据、僵持循环、`calls_orphaned` 指标
- `tihu-cli evolve` 与 `tihu-cli nash`

**验收**

- [ ] 候梯人数远超运载能力时，**死锁一定会被触发**。这是红线 6 的测试，用一个刻意饿死的场景跑
- [ ] 死锁期间该轿厢名下的外呼能观察到 `calls_orphaned`，且支持重分配的 Assigner 能明显救回来
- [ ] 关闭开关时走快路径，结果与旧版本一致
- [ ] 多日演化能画出逐渐恶化的曲线，且最后一天所有人的耗时都比第一天差

## 之后的候选

这一节不是承诺，是留位。每条都要先回答「它能不能改变买房决策或者调度算法排名」。

- 大件物品进电梯，比如电动车和装修材料，这是超载的真实诱因之一
- 多个单元各自的梯群，而不是一栋楼一个大群
- 中间层分区或单双层停站策略
- 待机层的优化配置
- 逐日的乘客学习 effect，也就是住户根据昨天的体验调整出门时间
