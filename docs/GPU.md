# 异构加速评估 GPU

这份文档回答一个问题：**梯户模拟器要不要上 GPU，上哪一种。**

结论先说：**当前形态下不要上 GPU，用多核 CPU 就够。** 下面把理由、可选项、以及
如果将来真要上该怎么上写清楚。末尾附一份当前代码的缺漏清单，因为结论是
「架构合理」，那就得把细节补齐。

---

## 1. 先看要加速的是什么

一次仿真跑一栋楼的一次早高峰。实测单跑耗时在毫秒量级，见
[`PERFORMANCE.md`](PERFORMANCE.md)。真正的重活不是一次跑，是一次要跑十万次。

```
十万组参数 × 二十个种子 = 两百万次单跑
两百万 × 3 毫秒 ≈ 一小时半的单核时间
```

这两百万次之间**互不依赖**。改一组参数不影响另一组的任何数字。这种结构叫
易并行，最适合的处理器是多核 CPU，不是 GPU。

GPU 擅长的是「同一段代码作用在几百万个元素上」。我们这里是「两百万人各自跑一段
不一样的代码」。两件事的脾气对不上。

### 1.1 一次仿真内部能不能并行

不能，而且原因不是实现懒。

事件驱动的主循环是一个优先队列。下一个处理哪个事件，取决于上一个事件改了什么。
轿厢 A 停下之后，谁派给轿厢 B 会变，未来的事件时刻会变。这条因果链没法拆。

就算硬拆，浮点求和的顺序一变，逐位可复现就没了。而 `AGENTS.md` 第 2.4 条把
逐位可复现列成红线。

改成固定步长就能并行，那会丢掉两样东西：门开关这种两秒级的过程会被抹平，
以及事件时刻变得不再精确。这两样正是结果可信度的来源。

**所以 GPU 在这条路上帮不上忙。** 下面列的可选项，前提都是「哪天真出现了一个
必须用 GPU 的固定步长变体」。

---

## 2. 可选的异构计算方案

按与本仓库的契合度从高到低排。

### 2.1 计算着色器，走 WebGPU 或 wgpu

wgpu 是 WebGPU 标准的 Rust 实现，一套代码跑 Metal、Vulkan、Direct3D 12，还能
编译进浏览器。

**它是这份清单里最合适的。** 三条理由。

内核已经要编译到 wasm，WebGPU 是浏览器里唯一能用的 GPU 接口，同一条技术路线
不用再分叉。wgpu 是纯 Rust crate，不引 C 工具链，不破坏「内核无外部依赖」。
一台 Mac 上写完，Windows 与 Linux 上大概率直接能跑。

代价是计算着色器只支持比较弱的着色器语言，没有指针，没有动态调度，共享内存
要自己规划。写一个和 CPU 内核逐位一致的 GPU 版本非常难。

### 2.2 Vulkan 计算，走 ash 或 vulkano

比 WebGPU 低一层，控制更细，桌面上覆盖最广。代价是样板代码多出几倍，还得自己
管内存屏障与队列族。浏览器里用不了。

它比 2.1 的唯一优势是能用到厂商特有的扩展。本仓库不需要那种东西。

### 2.3 OpenCL

跨厂商覆盖最广，老硬件也能跑，这一条是真的。

但它在苹果平台上已经废弃，macOS 10.14 起不再随系统更新，现在只能靠兼容层。
而本仓库的主要开发机就是 macOS。另外它要引一个 C 语言的运行时与 ICD 加载器，
与「不引入新依赖」的约定冲突。

**如果目标是「多种异构平台」，OpenCL 不是首选。** WebGPU 的覆盖面已经够，
而且不用碰 C 工具链。

### 2.4 SYCL 或 oneAPI

Intel 主导，对 Intel GPU 与 FPGA 友好。工具链重，苹果与 ARM 上支持差。
本仓库没有 Intel 专属硬件的诉求。

### 2.5 CUDA 与 HIP

CUDA 锁死 NVIDIA，HIP 锁死 AMD。都不支持苹果。用了它们，「多种异构平台」
这个目标当场作废。

### 2.6 Metal

只覆盖苹果。本仓库要跨平台，直接排除。

### 2.7 一个更朴素的方案：向量化与多线程

不上 GPU，只做两件事：把扫描任务交给多核，把能批处理的算术写宽一点。

对「两百万次独立单跑」这类负载，八个核就是八倍，实现成本接近零，还不破坏逐位
可复现。**在当前的负载形状下，这比任何 GPU 方案都划算。**

## 3. 如果哪天真的要上 GPU

三件事必须先做到，否则做出来的东西没人敢用。

1. **固定步长变体与事件驱动变体并存，共享同一套参数与指标。** 两者跑出来的
   平均等待要对得上，差多少要说明白。做不到这一点，GPU 版本就是一个无法验证
   的黑箱。
2. **只在扫描这一层用 GPU。** 一次着色器调用处理一批参数组合，每组合独立推进。
   不要把一次单跑拆到多个线程上，那会引入跨线程同步，把确定性的好处全部抵消。
3. **保持内核单一。** 要么 GPU 版本是内核里一份可选的执行后端，要么它就待在
   扫描工具里，不往 `tihu-core` 里塞第二套语义。`AGENTS.md` 第 2.1 条不接受
   两份计算逻辑。

## 4. 当前代码的缺漏清单

结论既然是「事件驱动架构合理」，那就得承认它还欠不少东西。按优先级列。

### 4.1 外壳还空着

| 位置 | 状态 |
| --- | --- |
| `crates/tihu-cli/src/main.rs` | 只有 `fn main() {}`。没有 run、sweep、bench、evolve |
| `crates/tihu-wasm/src/lib.rs` | 约九百行，手写 ABI，配置 JSON 进报告 JSON 出，见 `ARCHITECTURE.md` 第 7 节 |
| `web/` | 六个文件，无框架无依赖，`make single` 产出双击可用的单文件版 |
| `benches/` | 空。所有性能数字都还没有 |
| `harness/` | 空。红线验收脚本没写 |

网页这条腿有了，命令行的 `run` 子命令还没有。README 承诺的两条腿，目前一条。

### 4.2 统计口径欠账

| 项目 | 状态 |
| --- | --- |
| `detour_seconds` | 反向叫梯的绕行时间没有单独计量 |
| `car_load_avg` | 平均载客率没算 |
| `stall_max` | 单次最长僵局没记 |
| RTT | 用的是「空车出发到空车返回」的代理口径，不是解析式那一套 |

### 4.3 行为建模欠账

| 项目 | 状态 |
| --- | --- |
| 转向层 | `reversal_floor` 记了，但没有真正按它约束行程。反向叫梯者应该一路坐到折返点再下来，现在靠路由自然带过去 |
| 同行团 | `party_window_s` 是空参数。同户乘客按户聚合了，但没有按到达时间窗并团 |
| 满载直驶 | 已接上，是 `sim::step_car` 里的内核行为，与走哪个 router 无关。早先另有一个只做直驶的 router，实测与集选逐位相同，已删 |
| 多呼多台 | 只在独立面板下成立，且固定呼叫两台 |
| 逐日演化 | `Sim::days` 与 `StrategyMix::evolution_epsilon` 没有消费者 |
| 现场校准 | 没有 `calibrate`，所有待标定常数仍是行业经验值 |

## 5. 一句话总结

**不要把 GPU 放进关键路径。** 当前的瓶颈形状是「海量互不依赖的小任务」，多核
CPU 就是这个问题的最优解，而且它还保住逐位可复现。真要上异构后端，选 WebGPU
或 wgpu，并且只把它放在扫描这一层，先解决固定步长变体的验证问题再说。
